**E041 — FULLY RESOLVED (root-caused and fixed, not just cosmetically masked).** All of the CPU-side "missing trigger" leads below (the `object+21508` interface, the three independently-confirmed-dormant "rich lighting data" gates, the `0x82B6D128`/`sub_822ED860` state machine) were real and accurately traced, but turned out to be a dead end: a later live cross-engine comparison (our build vs. `xenia-edge`, both attached with `windbg-tool` at the identical guest address) found **the exact same empty/zero CPU state in both engines** - since Xenia renders the character correctly anyway, none of these fields could be the actual mechanism. The real cause, found via a cross-engine GPU shader-translation comparison (a custom SPIR-V disassembler against Xenia's compiled shader, and a verified-genuine DXBC dump against our own): Xenia's SPIR-V lowers the shader's `max`/`maxs` ucode instructions to the NaN-suppressing GLSL.std.450 `NMin`, while ReXGlue's DXBC translation does not reliably suppress NaN on every code path these shaders exercise - and the uploaded pixel float constants for the affected shaders genuinely do contain stray NaN bit patterns (7-16 per draw, confirmed live), which poison the downstream lighting math once they hit a non-NaN-suppressing operation. **Fix** (`src/graphics/d3d12/command_processor.cpp`, `D3D12CommandProcessor::UpdateBindings`): sanitize any NaN float to `0.0f` in the full uploaded pixel-constant range for the 11 known-affected material shaders, right before GPU upload - no synthetic color injected, no gate-forcing, real CPU-supplied data (including the legitimately-all-zero `c0`-`c9` static light slots) left completely untouched. This is a genuine data-hygiene fix, not an approximation: with only NaN removed, the shader's own otherwise-correct computation renders full, correct detail (skin tone, armor/leather shading, weapon detail) for both Conan and enemy NPCs. Confirmed via direct screenshot and by the user watching live gameplay ("esta solucionado"). The now-superseded `attempt-5`/`attempt-6` cosmetic patches (flat-color fill + gate-forcing; DXBC output-tint injection, the latter never shipped due to a regression) were removed from the source tree rather than left disabled, per this project's "don't leave speculative dead code" principle. **Fixed: E047 — jungle-level (second level) foliage rendered as giant stretched blade shapes.** Built a working DXBC disassembler this session (real `d3dcompiler_47.dll` `D3DDisassemble` via P/Invoke) and used an empirical isolation switch (`--e047_skip_shader=1|2`) to prove the cause was isolated to `F1B0F3E5D7061962` (a `kQuadList`-primitive vertex shader, emulated via `D3D_PRIMITIVE_TOPOLOGY_LINELIST_ADJ` + a custom ReXGlue-authored geometry shader). Exhaustive layer-by-layer verification (vertex shader ALU vs. ucode, GS declarations/NaN-discard, quad diagonal order, per-corner offset constants, final scale/world-offset constants) found every one of those individually correct. The actual root mechanism turned out to be simpler than any of that: **the game's own PM4 draw command requests exactly 4× more vertex reads (`host_draw_vertex_count`) than its own bound vertex-fetch constant declares buffer capacity for** — confirmed directly by reading guest memory past the declared capacity and finding clean, unwritten zeros. A degenerate all-zero vertex record makes all 4 corners of that specific quad collapse to a single point (same corner-offset constant read for all 4), and if that point lands near the camera's near plane, the resulting near-zero clip-space `w` after the camera transform blows the degenerate primitive up to fill much of the screen after the perspective divide - matching the observed symptom exactly. **Fix:** clamp `host_draw_vertex_count` down to what the bound buffer actually backs, for affected non-indexed draws, in `D3D12CommandProcessor::IssueDraw` (`command_processor.cpp`) - i.e. stop drawing the out-of-bounds portion instead of drawing it with garbage input.
