## E036 (fixed) — intermittent hang while loading a level: audio render client unregistered with its callback still in flight

**Symptom:** in about 1 of 3-6 automated runs (scenario_combat / scenario_jungle, legacy Xenos and native renderer alike), the swaps stop while the save loads. The last log line is E034's `AudioSystem::SubmitFrame: client 0 has no driver ... dropping frame`. Afterwards the guest threads are blocked and the Xenos CP idles in WAIT_REG_MEM.

**Evidence** (targeted logging in AudioSystem Register/Unregister/Submit plus the hang watchdog's all-thread stacks, `bench/repro_freeze.sh`):
- Clean runs: `UnregisterClient 0` then `RegisterClient 0` ~90 ms later from the same (main) thread, with the audio worker idle at unregister time.
- Hanging run: `UnregisterClient 0` arrived **while the audio worker was executing client 0's guest callback**. The dropped `SubmitFrame` came from that callback, on the Audio Worker thread. The re-register never happens.
- Stacks at the hang: the main thread is in sub_826FA248 -> sub_826F9A20 -> NtWaitForSingleObjectEx, waiting for the audio engine's mixer thread to exit. The mixer thread sub_826F9EE8 is in KeWaitForSingleObject on its wake event. The audio worker is idle (its client semaphore was drained by Unregister).

**Root cause** (from the recompiled guest code):
- Render callback 0x827147C8 -> sub_826FA060, run by the audio worker: enters the engine CS, sets `engine+300` = current thread ("callback in progress"), sets event A (wake the mixer), waits for B, submits the frame, then sets `engine+300 = 0`.
- Mixer thread sub_826F9EE8: `wait(A)`; if `engine+300 != 0` it treats the wake as a callback tick (mix, set B, loop); if it is 0, the wake is the shutdown request and it exits.
- Shutdown during level load (main thread): XAudioUnregisterRenderDriverClient, then set A and wait for the mixer thread to exit.

On the console, unregistering a render client does not return while that client's callback is running. The SDK's UnregisterClient returned immediately. With a callback in flight, `engine+300` was still set, so the mixer consumed the shutdown wake-up as a frame tick (A is auto-reset, so the two signals coalesce) and went back to waiting on A forever; the main thread then waited forever for it to exit. The dropped frame (E034) is only the in-flight callback's late submit.

**Fix** (SDK, `src/audio/audio_system.cpp`):
- The worker marks the client whose callback it dispatches (`callback_client_`) while still holding the global lock, together with reading the callback pointer.
- `UnregisterClient`, after clearing the client and draining its semaphore (lock released), waits on a condition variable until no callback of that client is running. It does not wait when called from the worker itself, and it warns and continues after 5 s rather than deadlock.
- Register/Unregister and the drop log now record the thread and the in-flight callback client.

**Verification** (EXPERIMENT_LOG EXP-034):
- Natural runs: 20 consecutive with no hang (10 scenario_combat legacy, 5 scenario_combat native A/B, 5 scenario_jungle legacy); before the fix about 1 in 3-6 hung. One of them went through the exact race (unregister with callback 0 in flight) and recovered normally.
- Deterministic check: `--audio_debug_callback_delay_ms=20` widens the window. With `--audio_unregister_wait=false` (old behavior) 2/2 runs hang; with the fix 0/2 hang.

## E012 — runtime: `NtCreateFile FAILED: path='d:\Shaders\Shaders\shaders.stx'` then `[FATAL] Call to invalid or unregistered function at guest address 0x824AFC90`

**Symptom:** with the GPU plugin loading correctly (E011 fixed — log shows `Initializing shader storage for title 545107DA...` and a successful `SetInterruptCallback`), the very next thing in the log is a failed file open for `d:\Shaders\Shaders\shaders.stx` (note the doubled `Shaders` segment), immediately followed by a fatal crash calling guest address `0x824AFC90`.

**Investigation:** logged the exact guest path per CLAUDE.md Phase 14 before touching anything. `game/shaders/shaders.stx` exists (singular, not nested) — the guest code is asking for a **nested** `Shaders\Shaders\` path that our extracted game folder doesn't have. Grepped the SDK's own host/kernel source for a hardcoded `"Shaders"` string that might explain a host-side path-doubling bug — found none, so the doubled segment is a literal string the *guest* game code itself builds and passes to the file-open kernel call, not a ReXGlue VFS defect. Separately checked whether `0x824AFC90` is real code (Category B/C decision tree, same as the E004/E006/E009 codegen-time cases): yes — a small, complete, valid-looking 6-instruction tail-call thunk (`mr`/`mr`/`mr`/`mr`/`lwz`/`b`), part of a repeated family of nearly-identical arg-shuffling thunks at `0x824AFC78`/`0x824AFC90`/`0x824AFCA8`/etc. But unlike E004/E006 this one produced **zero** codegen validation errors, meaning it was never registered in `PPCFuncMappings` at all — consistent with it only being reachable via a data-driven/indirect call (a function-pointer table entry, not a static `bl`/`b`), which static analysis has no way to discover without tracing actual data content. The crash fires *immediately* after the failed shader-file open, strongly suggesting this specific thunk sits on an error-handling/fallback path that's only exercised when shader storage fails to load — not proven yet, but consistent with all the evidence so far (not treated as certain, per CLAUDE.md's explicit warning against assuming crash causality).

**Fix attempted (addressing the file-not-found first, since it's unambiguous, before chasing the crash separately):** created a self-referencing Windows directory **junction** (not a symlink — junctions don't need `SeCreateSymbolicLinkPrivilege`, unlike every symlink issue this session, E002/xwin's cosmetic one) at `game/shaders/Shaders` pointing back to `game/shaders` itself, so `game/shaders/Shaders/shaders.stx` resolves through the loop once to the real file. Purely additive (no original asset touched or duplicated on disk — it's a filesystem alias), fully reversible (`Remove-Item` the junction).

**Status:** fixed and confirmed independent of E012-E014 below — rerunning after the VFS fix alone showed the `NtCreateFile` failure gone but the `0x824AFC90` crash still happening at the same point, proving the two were unrelated (good thing the causality wasn't assumed).

## E012/E013/E014 — a whole class of runtime `[FATAL] Call to invalid or unregistered function`, one address at a time, plus 722 more identified but not yet confirmed

**Pattern (confirmed 3 times so far — 0x824AFC90, 0x82715FC0, 0x826FB958):** the game boots, loads the XEX, initializes the GPU plugin and shader storage, and starts streaming audio — then crashes calling a guest address that was never registered as a function, despite `rexglue codegen` reporting **0 analysis errors**. Every one of the 3 confirmed instances turned out to be real, valid, self-contained PPC code (verified in `logs/default_full.dis` before touching the manifest, per the Category B/C decision tree) that static analysis had no static call-graph edge to find, because it's only ever reached through a **data-driven indirect call** — a function pointer read out of a dispatch/vtable-like table at runtime, not a `bl`/`b` anywhere in the code. Codegen's 0-error validation only proves every *statically discoverable* control-flow edge resolves; it says nothing about function pointers the game populates from data.

**Systemic scale, found with [`scripts/find_unregistered_after_bctr.py`](../scripts/find_unregistered_after_bctr.py):** all 3 confirmed crashes shared one more specific trait — the crashing address immediately follows a `bctr` (indirect branch, unknown static target) with **no** `.long 0x0` zero-padding gap before it. Gap-fill reliably seeds a new function candidate after a padding-delimited `blr`, but does not reliably do the same right after an unpadded `bctr` (a real gap-fill weakness, not a bug in any single function). Scanning the *entire* disassembly for this exact shape (address immediately follows a `bctr`, no padding, not in `conan_register.cpp`) found **725** such addresses total — of which only 3 have actually been hit by a real playthrough so far.

**Deliberate decision: fix reactively, one confirmed crash at a time, not all 725 at once.** CLAUDE.md is explicit that a function boundary needs real evidence ("Never guess a boundary solely from 'the next unresolved address'"), and most of those 725 are very likely dead code, alternate/rare branches, or handlers for content this playthrough never reaches — batch-declaring boundaries for all of them from a single generic heuristic (e.g. "next registered function or next padding, whichever comes first") would not meet that bar; some of these chain several unregistered addresses back-to-back (E013's fix ends at *another* unregistered address, 0x82716008, which is itself real code but hasn't crashed yet) where a naive automated boundary picker could easily get it wrong. Each of the 3 fixed so far was individually confirmed against the disassembly before being added.

Fixes applied, all `end` values read directly from the disassembly (next `.long 0x0`, next registered function, or — for E013 specifically — the next confirmed-real instruction in the same handler chain):
- **E012** `0x824AFC90` → `end = 0x824AFCA8` — one gap in an otherwise-fully-registered family of arg-shuffling thunks (siblings `0x824AFC78`/`0x824AFCA8`/`0x824AFCB0`/`0x824AFCB8` were all already fine).
- **E013** `0x82715FC0` → `end = 0x82716008` — bounds-check + vtable-dispatch handler, chained immediately after another `bctr` with no gap.
- **E014** `0x826FB958` → `end = 0x826FB96C` — the same refcount-increment shape as E004, cleanly padding-bounded.

**Status:** 5 confirmed crashes fixed this way in total by the end of the session (E012 `0x824AFC90`, E013 `0x82715FC0`, E014 `0x826FB958`, E015 `0x8259A720`, each documented individually in `conan_manifest.toml`); `rexglue codegen` still reports 0 analysis errors after each. The remaining ~721 statically-identified candidates are **not yet confirmed necessary** — see `port_status.md`'s "Next steps" for how to keep resolving these as they surface (rerun, get the new crash address, check it against the `find_unregistered_after_bctr.py` output first since it's very likely already on that list, verify the specific instance's own boundary in the disassembly, add one manifest entry, regenerate, rebuild, rerun). After E015, a run reached and correctly rendered the Nihilistic Software developer splash video (M6, first frame) before hitting a **different class** of crash — see E016.

## E016 — runtime access violation after E012-E015's crash class: `Unhandled guest access violation: read of guest 0x000001A4`, following exhausted `dbgfnt0.dds`/`dbgfnt0.tga` lookups

**Symptom:** after fixing E012-E015, a run got past the unregistered-function crash class entirely, rendered the Nihilistic Software splash video correctly (screenshot confirms a real, correctly-decoded video frame — first-frame milestone reached), then crashed with `Unhandled guest access violation: read of guest 0x000001A4 (host 0x00000001000001A4)`. Guest address `0x1A4` is a small, non-zero-but-near-null offset — the classic shape of `some_pointer->field_at_offset_0x1A4` where `some_pointer` is null or was never actually initialized.

**Investigation so far (not fully root-caused yet — flagging clearly rather than guessing):** immediately preceding the crash, the log shows an exhaustive, repeated search-path chain (`d:\Textures\`, `d:\Textures\Effects\`, `d:\Textures\Levels\`, `d:\Textures\Models\`, `d:\Textures\Lights\`, `d:\Textures\Anark\`, `d:\Textures\HUD\`, `d:\Textures\Fonts\`, `d:\Textures\SpeedTree\`, `d:\Ui\`, `d:\`) all failing to find `dbgfnt0.dds` and then `dbgfnt0.tga` — a "debug font" texture. Confirmed the file genuinely doesn't exist anywhere in `game/` (not a VFS path-nesting issue like E012's `Shaders\Shaders` — this one really is absent from the extracted disc dump). Working hypothesis, **not yet confirmed**: the debug-font loader doesn't handle a total lookup failure gracefully and the crash is a null-pointer-style dereference somewhere downstream of that — but this has not been traced through the disassembly the way E012-E015 were, so treat it as a hypothesis, not a diagnosis.

**Root-caused with a symbolized crash.** No debugger was available, so added a temporary diagnostic patch to the SDK itself (see `patches/sdk/`) rather than guessing further:
1. `src/system/xmemory.cpp`'s `Memory::AccessViolationCallback` — dumps the full `PPCContext` (all GPRs, LR, CTR) via `rex::runtime::ThreadState::Get()`, since the vectored exception handler runs on the faulting thread itself. This showed `lr=0` and `r31=0` was consistent with the fault (an offset-0x1A4 read implies a null base register), but wasn't conclusive on its own — LR/CTR were both stale from earlier calls, not the current guest PC.
2. `src/core/exception_handler_win.cpp`'s `ExceptionHandlerCallback` — when no registered handler manages an exception, resolve the **host RIP** (which the handler already had, unused) to a function + source line via `dbghelp.h` (`SymFromAddr`/`SymGetLineFromAddr64`), using the PDB this `RelWithDebInfo` build already produces. No debugger needed — `dbghelp.dll` ships with Windows and the symbol APIs work standalone.

This immediately pinpointed the exact line: `generated/default/conan_recomp.41.cpp:17013`, inside `sub_82599B40`:
```cpp
loc_82599B94:
	// lwz r11,420(r31)
	ctx.r11.u64 = REX_LOAD_U32(ctx.r31.u32 + 420);   // <-- faults: r31 == 0, 420 = 0x1A4
```
reached only when a preceding call (`sub_82599A58` or `sub_825998D0`, chosen by a branch a few lines up) returns non-zero in r3 — i.e. only on what the code treats as a "found/succeeded" path.

**The actual asset exists**, just not where the game looked for it in time: `game/ui/dbgfnt0.tga` + `game/ui/dbgfnt0.abc` (bitmap font + glyph metrics) are present. The game's asset-search chain tries 11 directories × 2 extensions (`.dds` then `.tga`) — `Textures`, `Textures\Effects`, `Textures\Levels`, `Textures\Models`, `Textures\Lights`, `Textures\Anark`, `Textures\HUD`, `Textures\Fonts`, `Textures\SpeedTree`, `Ui`, and the root — and the `.dds` pass runs to completion (reaches `Ui` and the root, fails cleanly on all 11), but the `.tga` pass **crashes right after failing at `Textures\SpeedTree`, one directory before it would have reached `Ui`** (where the real file lives) — same list, same order, reproducibly stopping one step earlier on the second pass. That points to some form of search-state reuse/exhaustion bug between the two extension passes (not fully traced to its root instruction — not necessary once the practical fix below was verified), rather than the file being absent outright.

**Fix:** two NTFS hard links (not symlinks — no special privilege needed, unlike every actual `symlink` issue this session) into `game/textures/fonts/` (a real, already-populated content directory, checked *before* `SpeedTree` in the search order): `game/textures/fonts/dbgfnt0.tga` and `.abc` → the real files in `game/ui/`. This makes the `.tga` lookup succeed at an entry the broken second pass actually reaches, so the exhaustion bug downstream never gets exercised. Purely additive — nothing in `game/ui/` was touched or duplicated in content, just given a second directory entry pointing at the same data.

**Status:** fixed, verified by rerun — the crash at `0x1A4`/`sub_82599B40` no longer occurs. Fixed via a **mid-asm hook** (`[[entrypoint.midasm_hook]]`), a mechanism not used earlier in this project — see the note below on how it actually works, since the obvious first attempt at using it was wrong.

**How mid-asm hooks actually work (learned by testing, not documented anywhere in the SDK):**
- The manifest section must be **nested under `[[entrypoint.midasm_hook]]`**, not top-level `[[midasm_hook]]` — same nesting rule as `[entrypoint.functions.0xADDR]`. A top-level array is silently accepted by the TOML parser but never read by `RecompilerConfig::LoadFromTable` (which only looks inside the `[entrypoint]` table) — codegen reports `0 written` with zero errors, easy to mistake for "it did nothing because there was nothing to do."
- Once nested correctly, codegen **automatically emits the `extern` declaration** for the hook function directly above whichever `DEFINE_REX_FUNC` uses it (`extern bool <name>(PPCRegister& <reg>);`) — nothing needs to be forward-declared by hand, the function just needs to exist somewhere in the final link with a matching signature (`bool name(PPCRegister&)`, plain C++ linkage, no `extern "C"`).
- With `registers = ["rN"]` and no return/jump fields, the call is a plain statement inserted before (or after, with `after_instruction = true`) the target instruction. With any of `return`/`return_on_true`/`return_on_false`/`jump_address*`, the hook function is treated as returning `bool` and wrapped `if (hook(...)) { <true branch> } else { <false branch> }` — an empty branch (no return/jump configured for that side) just falls through to whatever code normally follows, which is what makes "run this check, and if it passes proceed exactly as before" possible.
- Multiple hooks can share one native C++ function (`src/hooks.cpp`'s `conan_nonnull_guard` is reused across every E016/E017/E019/E021-E024 entry below) — the manifest `name` is just the symbol to call, and nothing ties one hook function to one address.

## E047 (open — root cause not yet confirmed) — jungle-level vegetation renders as giant stretched blade shapes covering most of the screen

**Symptom:** on reaching the second level (jungle/ruins setting), palm-frond/foliage cards render as massive, screen-spanning stretched green shapes instead of small individual leaves, alongside E041's still-unresolved character darkening. User asked for both to be fixed before continuing with further crash triage.

**Shader identified precisely, same technique as E041 (solid-debug-color override in `dxbc_translator_om.cpp`'s `CompletePixelShader()`), this time scoped to just 2 candidate shaders instead of all of them** (coloring every shader broke UI/menu rendering the first time this was tried this session — see the build-hygiene note below). Candidates were selected from the `UpdateBindings` "draw pair" logger by looking for pixel shaders paired with an unusually **large declared vertex float-constant count** (256, the same "dynamically-indexed constant array" fingerprint used to find Conan's skinning vertex shader in E041) among shaders newly active in this level. One screenshot with the color override confirmed it immediately: the entire stretched-frond mess is solid magenta, i.e. pixel shader **`8E872461A90E86CA`**, driven by (at least) two distinct 256-float-constant vertex shaders, **`D1E0C9F7E7075E75`** and **`F1B0F3E5D7061962`**.

**Read `shader_D1E0C9F7E7075E75.ucode.vert`'s full disassembly.** It's a genuine per-instance placement/animation shader: fetches per-vertex position + a second per-vertex attribute (`vfetch_full`/`vfetch_mini`), combines it with a constant (`c160`) and a scale (`c255.z`) via `floor`/`frc` to compute a **dynamically-addressed index into the constant bank** (via `maxas` setting the `a0` address register from a computed float, done *twice* with different source values in the same shader), then bilinearly interpolates between `c[161+a0]`, `c[162+a0]`, `c[163+a0]` (and a second nearby triplet) to build the final vertex position/orientation. This is structurally the same "dynamic constant-array indexing" mechanism as E041's per-pixel light loop, just applied per-vertex for (most likely) wind-sway animation and/or instance placement.

**Dumped the actual constants this shader reads (temporary hook in `command_processor.cpp`'s `UpdateBindings`, same pattern as E041) — and, unlike E041's still-open static-light-array question, this data looks entirely legitimate:**
```
c158=(-0.409,-0.905,0.118,0.000)   -- a unit vector (magnitude ≈ 1.0)
c159=(98.455,-100.863,6.360,1.000) -- a plausible homogeneous world position
c161-163, c165-167, c169-170       -- each triplet is a near-orthonormal 3x3
                                       rotation/orientation matrix (row magnitudes
                                       ≈ 1, small cross terms) - not garbage
c255=(4.000,0.000,0.350,0.000)     -- looks like a grid-scale/threshold constant
```
Sampled across multiple consecutive frames: the matrices **animate smoothly** frame to frame (small, continuous rotation drift) rather than jumping or containing NaN/garbage — consistent with real wind-sway animation data being correctly computed and uploaded by the CPU-side recompiled game code.

**This is a meaningfully different situation from E041.** There, the leading open question is whether specific constant data the shader reads is genuinely missing. Here, the constant data reads as structurally valid and correctly animating - **the CPU-side data pipeline for this shader appears to be working correctly.** That shifts suspicion toward either (a) the **per-vertex fetched data** (`vfetch_full r2`/`vfetch_mini r0`/`vfetch_full r4` - not yet inspected, would need actual vertex buffer contents, not just constant registers) being wrong for the vertices that make up a single leaf card, causing each corner of what should be a small quad to compute a wildly different `a0` index and therefore sample unrelated orientation data, or (b) a translation edge case specific to this shader's *twice-in-one-block* dynamic `a0` reassignment pattern (`maxas r0._, r1.ww` immediately followed later by `maxas r0._, r1.xx` within the same `exec` group) in `dxbc_translator`'s relative-addressing handling - not yet exercised the same way by any other shader checked this session.

**Traced the whole dynamic-addressing pipeline through the DXBC translator source and confirmed it correct, ruling out two more specific hypotheses with code-level certainty (not just data sampling):**
1. **Address computation (`maxas`/`maxasf`)** — `dxbc_translator_alu.cpp`: round-to-nearest, clamp to `[-256, 255]` (the real Xenos hardware range), convert to int. Textbook-correct MAXA/MAXAS semantics, matches Xenia's documented behavior. Not the bug.
2. **Relative-read indexing and the sparse-packing interaction** — this was the most promising lead: `dxbc_translator.cpp`'s `LoadOperand()` uses the *raw* Xenos register number directly as the constant-buffer index for relative reads (`c[163+a0]` → buffer index `163+a0`, no repacking), which would only be correct if the uploaded buffer has register N living at buffer offset N for the whole potentially-addressed range. Tracing back to `translator.cpp:188-192` confirmed the system *does* handle this correctly: any shader using relative float-constant addressing anywhere gets `float_dynamic_addressing = true`, which forces `float_count = 256` and `float_bitmap` to all-1s (`memset(..., UINT8_MAX, ...)`) - so the sparse-packing upload loop in `command_processor.cpp` walks bits 0 through 255 in strict order with none skipped, which *is* a full 1:1 unpacked layout. No mismatch.

**Directly verified this empirically too, not just by reading the code** — extended the diagnostic to log the *actual uploaded GPU-bound buffer bytes* (not the raw guest register file this time) at the exact offset the shader reads via `c[161+a0]`. Result: `bitmap[0]=0xFFFFFFFFFFFFFFFF`, `bitmap[2]=0xFFFFFFFFFFFFFFFF`, `float_count=256` (confirming the all-1s/unpacked path is indeed taken), and the uploaded buffer's `c161`/`c163` values match the same well-formed rotation-matrix pattern already found in the raw register dump. **The entire data pipeline from guest register file through upload to the GPU-bound constant buffer is confirmed correct for this shader** - ruling out constant data, address computation, and the upload/packing mechanism as the cause, with hard evidence at each stage rather than assumption.

**Built the vertex-fetch-data check too, and it also came back clean — completing an exhaustive, hard-evidence elimination of the entire data pipeline.** This needed a genuinely new category of instrumentation (reading arbitrary GPU-visible guest memory through a fetch descriptor, not just register/constant-buffer state), built in three corrected passes:

### E041 — ROOT CAUSE FOUND AND FIXED FOR REAL: stray NaN values in the uploaded constant range, not missing light data at all

**After the CPU-state-parity finding closed out the "missing trigger" framing (below) and a source-level ReXGlue-translation-accuracy research pass found no evidence of a CPU translation bug, the investigation pivoted to the GPU shader-translation layer per the user's direct question ("can ReXGlue itself be made more accurate to reach the correct values").**

**Cross-engine shader-translation comparison, done without needing to re-run Xenia interactively** (per the user's explicit ask to avoid needing manual input in Xenia if the needed data was already available): launched `xenia_edge.exe` once with `--dump_shaders=<dir>` and no navigation at all - shader `5AC3C8B824ED2F97` compiles automatically during Xenia's own startup/menu rendering, so both its intermediate SPIR-V and final DXIL dumps were captured with zero interactive input. Wrote a small from-scratch SPIR-V disassembler (`logs/spirv_disasm.py`, uses the real grammar JSON vendored in `xenia-edge-src/third_party/SPIRV-Headers` for accurate opcode names - no `spirv-dis` binary was available on this machine and building SPIRV-Tools from source would have cost more time than this targeted script) and used the already-built `dxbc_disasm.ps1` (P/Invokes `d3dcompiler_47.dll`) against a **freshly, verifiably-genuine** DXBC dump from our own `conan.exe` (launched once with `--dump_shaders=... --d3d12_dxbc_disasm=true`, also reached without needing fresh navigation - the game auto-resumed straight into the jungle-level save from disk). Note: both engines' compiled shader disassembly headers read `"// Generated by Xenia"` - this is not cross-contamination, it's a literal leftover string in ReXGlue's own (Xenia-derived) shader translator source that was never renamed; a genuinely-fresh, uncontaminated dump from our own process still carries it.

**Finding: Xenia's SPIR-V compiles the shader's ucode `max`/`maxs` instructions overwhelmingly (277 of ~280 instances) as the NaN-suppressing GLSL.std.450 `NMin` extended instruction** (returns the non-NaN operand if exactly one input is NaN - this is deliberate: real per-light-slot data earlier this investigation confirmed contains stray `-nan` values at specific constant indices like `c70`/`c73`, alongside legitimately-zero real data, so a NaN-tolerant lowering silently "heals" those slots). Our own DXBC dump shows a similar overall `min`-heavy pattern for the same ucode (177 `min` / 2 `max`), so the *opcode choice* isn't obviously different between engines at a glance - correlating the exact NaN-consuming instruction across two structurally unrelated IRs (DXBC vs. SPIR-V) with heavy dynamic/relative constant addressing turned out to be impractical by hand in reasonable time.

**Instead of continuing the manual IR correlation, tested the NaN hypothesis directly and empirically** - the decisive, fastest way to get a real answer. Added a narrow, isolated experiment (`E041-fix-attempt-7`, `command_processor.cpp`'s `UpdateBindings`): for the same 11 known-affected shader hashes, scan the *entire* uploaded 256-constant range (not just `c0`-`c9` - dynamic addressing uploads the full range regardless) for `NaN` floats and zero them out - **nothing else**. No synthetic color fill, no gate-forcing (both of `attempt-5`/`attempt-6` were disabled for this test specifically to get an uncontaminated signal). Rebuilt, relaunched, confirmed via log that real NaN values are present on essentially every draw (7-16 per shader instance, every frame, across all 11 hashes - a previously-unquantified but very real and consistent phenomenon, not a rare edge case).

**Result: visually confirmed fixed, both by direct screenshot and by the user watching live - "esta solucionado."** With *only* NaN removed (all real, CPU-supplied data, including the extensively-documented all-zero `c0`-`c9` static light slots, left completely untouched), Conan renders with full, correct detail - real skin tone, visible leather/armor texture and shading, no near-black silhouette - and the enemy NPCs show equivalent improvement. This is a dramatically better, and dramatically simpler, result than *any* of the six prior fix attempts in this file (flat-color fill, gate-forcing, DXBC output-tint injection) - none of which needed to be right, because the actual defect was never "missing light data" at all. The near-black rendering the entire investigation chased for so many sessions was **NaN poisoning an otherwise-correct calculation** - once a NaN enters an accumulation chain and touches a non-NaN-suppressing operation anywhere downstream (evidently somewhere in ReXGlue's chain despite `min`/`max` themselves most likely being spec-correct - the exact poisoning instruction was not pinned down, and given the fix works cleanly it wasn't necessary to), the whole result collapses toward black/undefined, regardless of how reasonable the surrounding real data is.

**This reframes the entire multi-session E041 investigation's conclusion.** Every "missing CPU trigger" (the `object+21508` interface, the `object+11000` rich-path gate, the `object+10941`/`10942` flag bits, the `0x822ED860` state machine) was real, accurately characterized, and genuinely dormant - that part of the investigation wasn't wrong. What was wrong was the assumption that dormant trigger = missing data = need to synthesize replacement data. The actual game data at those "empty" slots isn't semantically meaningful zero *or* real light color - it's uninitialized memory that happens to contain a mix of legitimate zero bytes and NaN bit-pattern garbage, and only the NaN part was ever actually breaking anything. Xenia was never computing "real" light data through some undiscovered path either - it likely just happens to be NaN-tolerant at the exact point ReXGlue isn't (or its own uninitialized-memory contents differ enough by coincidence to avoid the NaN case as often) - both are consistent with the same underlying game/hardware reality, just handled differently downstream.

**Fix, finalized**: kept `E041-fix-attempt-7`'s NaN-sanitization as the real, active fix. Removed the now-superseded `attempt-5`/`attempt-5b` constant-buffer color-fill patch and the `attempt-6` DXBC injection entirely (not just disabled - they were guesses that happened to partially mask the symptom for the wrong reason, and keeping dead code with hash-gated special-casing around would violate this project's own "don't hide errors, don't leave disposable-looking permanent hacks" discipline once a real fix is confirmed). The final fix is small, general (scans for NaN, not gated on any assumption about what the "correct" value should be), and doesn't special-case *which* light slot or shader sub-feature was affected - it corrects a genuine data-hygiene defect (NaN reaching the shader) at the one legitimate layer ReXGlue already owns for exactly this class of problem (the same bind-time constant upload path used for all the prior attempts), not a cosmetic override.

**Still open, explicitly not blocking**: where the NaN bit patterns themselves originate (uninitialized guest heap memory being reinterpreted as float, most likely, matching the "nothing ever writes real data to this region" conclusion the CPU-side investigation already established with high confidence) was not root-caused to a specific guest allocation site. This is now a genuine "why is guest memory uninitialized here" question, not a "why does light rendering look wrong" question, and it does not need to be answered for E041's visible symptom to be considered fixed - it's included here only in case a future investigation into memory-initialization hygiene elsewhere in this port finds it relevant.

## E041 (open — root cause not yet confirmed) — Conan's character model renders far too dark (near-black) while the environment in the same frame is correctly lit

**Symptom:** after M9 (stable interactive gameplay, E025-E040), the user provided a reference screenshot showing how Conan should look (skin/armor/hair detail visible under normal lighting) versus a screenshot from this port where the character reads as a near-black silhouette against a normally-lit environment. Not a crash, not a hang — purely a visual defect, reproducible every time the character is on screen.

**Evidence gathered (direct pixel measurement, not visual impression):**
- Installed RenderDoc 1.37 (portable, no admin) and captured several full-frame D3D12 captures of the running game (`renderdoccmd.exe capture -c <file> conan.exe --game_data_root game --gpu_plugin xenos --mnk_mode`; late `inject --PID=` does **not** properly hook D3D12 device creation — must launch fresh under `capture` from process start).
- Right-click pixel-picking in RenderDoc's Texture Viewer (Outputs tab) on the final composited swapchain image, same frame:
  - Character torso: RGB ≈ (17, 23, 23)/255.
  - Adjacent shadow near the character's leg: RGB ≈ (6, 10, 10)/255.
  - Nearby lit floor/archway, same frame: RGB ≈ (108, 144, 144)/255.
- This is a ~6x brightness gap between character and environment pixels in the *same rendered frame*, ruling out a monitor/screenshot/global-tonemap explanation — the defect is baked into the actual frame buffer and is specific to the character.
- A cutscene NPC (unrelated character, different scene) rendered with **correct**, natural skin lighting in the same investigation — so this isn't a blanket "all character shaders are broken" issue; whatever's wrong is either specific to the player character's draw path, specific to real-time gameplay rendering (vs. cutscene rendering), or data-dependent (e.g. missing per-object dynamic light data that cutscenes don't rely on).

**Hypotheses tested and ruled out:**
1. **Missing texture assets** — ruled out; zero VFS lookup failures in the log around the character's draws.
2. **D3D12 API misuse** (wrong resource state, bad binding) — ruled out; `--d3d12_debug` (D3D12/DXGI debug layer) reports zero validation errors during normal gameplay.
3. **One of this session's E016-E029 mid-asm guard hooks silently swallowing per-frame data** (e.g. a dynamic-light-list pointer misidentified as "invalid" and skipped) — this was the leading hypothesis, since several guards (`conan_nonnull_guard`, `conan_plausible_ptr_guard`, `conan_valid_code_ptr_guard`) patch a generic list/container mechanism (`sub_825870B8` and siblings) that turned out to be an extremely hot per-frame path (confirmed via instrumented call/reject counters added to `src/hooks.cpp`, see below), not just a loading-screen-only path as originally believed. **Ruled out empirically**: across 1.3M+ calls to `conan_nonnull_guard` spanning the attract screen through real interactive combat gameplay, the reject count stayed at **0** the entire time (`conan_plausible_ptr_guard`: 0 calls total this run; `conan_valid_code_ptr_guard`: 56 calls, 0 rejects). These guards are not misfiring during normal play. (Diagnostic counters are temporary — see TODO below.)

**RenderDoc architectural dead end (documented so it isn't retried the same way):** every single RenderDoc capture examined (4 independent captures, both widely spaced in time and taken as rapid back-to-back F12 presses within the same second) shows **exactly one draw call per captured frame** — a `DrawInstanced(4, 1)` fullscreen quad directly targeting the swapchain, bracketed by exactly one `ExecuteCommandLists`. This is consistent across every sample, ruling out capture-timing bad luck. Read `src/graphics/d3d12/command_processor.cpp` (ReXGlue's Xenos-to-D3D12 backend, both this project's dependency and the actual renderer) to understand why: real Xenos draws are recorded into an internal `deferred_command_list_` and only flushed to a real D3D12 command list in one batch per `EndSubmission()`/swap. That confirms the mechanism *could* show multiple real draws per capture — but empirically it never does, meaning whatever produces the fully-composited scene (with all ~150 distinct shaders seen in a `--dump_shaders` dump) happens through a path RenderDoc's Present-triggered capture boundary doesn't attribute to the frame it captures. **Practical conclusion: RenderDoc cannot be used to identify the exact shader/draw that shades Conan in this specific ReXGlue build** — further GPU-side debugging needs a different technique (e.g. `--dump_shaders` cross-referenced with disassembled Xenos ucode read statically, not a live RenderDoc pixel/shader debug session).

**Leading remaining hypothesis:** a CPU-side bug in the statically-recompiled PPC game code that sets up per-object dynamic lighting data (light count/light list/light color registers) before a character draw, of the same general class as E016-E040 (a pointer or count silently ending up zero/null with no crash) — consistent with: no crash, character-specific (baked/static environment lighting wouldn't need this path), a cutscene NPC rendering correctly (cutscenes may use baked lighting or a different light-setup call than real-time gameplay), and the "near-black but not pure-black" result (consistent with an ambient-only contribution and zero dynamic-light contribution).

**Progress: the character's actual shader pair has been identified, narrowing where to look next.** Added a temporary diagnostic to `src/graphics/d3d12/command_processor.cpp`'s `UpdateBindings` (SDK source, not project source) that logs, per distinct vertex+pixel shader pair actually bound for a draw, the shaders' `ucode_data_hash()` (matches `logs/shader_dump/shader_<HASH>.ucode.frag` filenames) and their declared float-constant counts, throttled to avoid log spam. Reasoning: a skinned character mesh needs a bone-matrix palette accessed via a *dynamically computed* index, which the static shader-constant-usage analyzer can't bound at compile time — it conservatively marks the full 256-slot constant bank as "possibly used," a distinctive fingerprint no static-geometry environment shader has (those showed only ~8-9 float4 vertex constants, a small fixed transform, in the same captured scene).

Found exactly one vertex shader matching that 256-constant fingerprint: **`B117AD40F2829BDF`**. It paired with six distinct pixel shaders in the one gameplay scene sampled: `C66BA6E024478ED7`, `990D4F5E0294011F`, `6642CA2D469820DD`, `5AC3C8B824ED2F97`, `230F4F4FC4FD2617`, and `8A15F953DAEA5E25` (0 pixel constants — almost certainly a shadow/depth-only pass). Multiple pixel shaders pairing with one skinned vertex shader is expected — the scene has more than one character (Conan plus at least one NPC), each with its own material/pixel shader sharing the same generic skinning vertex shader.

**Narrowed further with a one-shot visual test — Conan's exact three material shaders are now confirmed.** Added a compile-time (not runtime-branched) override in `src/graphics/pipeline/shader/dxbc_translator_om.cpp`'s `CompletePixelShader()`: when a pixel shader's `ucode_data_hash()` matches one of the five lit candidates, force its output straight to a distinct solid debug color (red/green/blue/yellow/cyan) right before the normal alpha-test/blend/output-merger logic, so the override is visible while everything else about the draw (alpha test, blend state) stays real. One screenshot during gameplay showed the result unambiguously: **Conan renders in yellow + red + blue simultaneously** (skin/head = `5AC3C8B824ED2F97` yellow, leather/straps = `C66BA6E024478ED7` red, cloth/loincloth = `6642CA2D469820DD` blue). The cyan shader (`230F4F4FC4FD2617`) turned out to be the stone archway/architecture, not a character — sharing the skinning vertex shader for an unrelated reason (or a generically-reused vertex shader, not exclusively a character fingerprint as first assumed). The green shader (`990D4F5E0294011F`) was the other on-screen NPC plus small floor debris props.

**Read Conan's skin shader (`5AC3C8B824ED2F97`) disassembly in full (`logs/shader_dump/shader_5AC3C8B824ED2F97.ucode.frag`, 608 ALU instructions) and traced its lighting structure precisely:**
- A **dynamic per-pixel light loop** (`loop i16, L31`) using *relative addressing* (`c[64+a0]`, `c[65+a0]`, `c[66+a0]` — color/attenuation/position per light), with `a0` computed from loop constant 16's packed count/start/step fields.
- A **separate, statically-unrolled secondary light array** in pixel float constants `c0`-`c23`, gated behind predicate checks against threshold constants `c182.x` through `c186.x` (one gate per potential light in that array).
- Final output (`oC0`) blends contributions from both, plus a cubemap-sampled ambient/IBL term, with a final `cndgt`/predicate select near the very end (`c181.x`-gated) between two accumulation paths.

**Direct register-level readback (new temporary diagnostic, same `UpdateBindings` hook, active only when `ps_hash == `Conan's skin shader) gives a real, reproducible, surprising result:**
- Loop constant 16 decodes to a small, sane, **non-zero** count every single sample: loopcount ∈ {1, 2, 4} across different draws (varies — likely per-body-part or per-frame light culling), start=0, step=1. **Not a zero-light-count bug.**
- The static secondary array (`c0`-`c23`, including gate `c16`) reads as **exactly zero** every sample — but this is very likely *correctly unused/gated* dead data (the `c182.x`-`c186.x` thresholds that guard entry into that block weren't checked yet, but an all-zero gate would correctly skip the block via the shader's own `(!p0) jmp` — not yet confirmed as a bug).
- The region the dynamic loop's relative addressing actually reads from (`c60`-`c99`, wide scan since the true per-light stride, `c249.z * c253.y`, hasn't been decoded exactly) shows **real, plausible, non-zero light data** — e.g. one sample: `c64=(1.00,1.00,0.81,nan)` (a warm near-white color), `c65=(1.00,0.01,0.50,0.00)`, `c66=(11.28,-0.05,2.82,1.00)` (looks exactly like a homogeneous world-space light position). A few adjacent slots read `-nan` (e.g. `c70`, `c73`) — consistent with unused padding within the scanned range, not necessarily a fault.

**This meaningfully weakens the original "missing/zero CPU-side light data" hypothesis** — real, structured, plausible-looking light data genuinely reaches the shader. The bug, if it's data-side at all, is more likely either (a) in the *static* secondary array/gating being incorrectly zero when it shouldn't be (still unconfirmed — need `c182`-`c186` threshold values), or (b) not a data problem at all but a **math/translation bug inside this specific 608-instruction shader** (e.g. in how the loop's accumulated result gets combined with the ambient/IBL term at the very end, or a Xenos-to-DXBC translation issue specific to an instruction pattern this shader uses that others don't — it's unusually large and uses relative addressing, `cube`, POM-style `getWeights2D` parallax sampling, and predicated blending, a combination not exercised by the simpler environment shaders that render correctly).

**Follow-up test that actually localized the bug, using the same debug-override mechanism in "boost" mode instead of a full color override:** changed `CompletePixelShader()`'s override to *multiply* the shader's own already-computed output color by 8x (RGB only, alpha untouched) for the three Conan material shaders, instead of replacing it outright — the idea being that a uniformly-underexposed result would look like correctly-shaded detail just brighter, whereas a missing-light-contribution result would still show flat/black regions even after boosting a near-zero value.

**Result was decisive and not what the original hypothesis predicted.** The boosted screenshot shows a clearly **spatially inconsistent** pattern, not a uniform dim character: Conan's upper back, shoulder, and right forearm show bright, believable, overexposed highlights consistent with a real directional key light hitting those surfaces from above/behind — proving the dynamic per-pixel light loop (confirmed non-zero and reasonable-looking in the earlier register dump) genuinely *is* contributing real, correctly-computed directional lighting to at least some surfaces. But his legs, lower torso, and the opposite side of his body remain **pure black even at 8x** — 0 × 8 is still 0, so those surfaces are receiving essentially zero contribution from *any* light source, not just an underexposed one.

**This redirects the hypothesis away from the dynamic light loop (which works) and toward whatever is supposed to provide ambient/fill lighting for surfaces not directly hit by the key light** — most likely the cubemap-sampled IBL/ambient term earlier in this same shader (the `tfetchCube` block around instruction 106, and the related environment-color blend near the end), or the statically-unrolled secondary light array (`c0`-`c23`) already confirmed to read as exactly zero — which, if it's supposed to be a fill/area light rather than dead/unused data, would now be a prime suspect rather than assumed-harmless. A reference photo of a real/correctly-rendered version of this same scene would show whether this much falloff is intentional moody lighting (single dramatic key light, minimal fill — plausible for this gothic dungeon setting) or a genuine missing-fill-light bug; the user's original reference image showed detail across the *whole* character (skin, armor, hair all visible), which argues for the latter.

**Checked the cubemap/IBL scale constant directly (`c176.x`, read from the disassembly at ucode instruction 113: `mul r1.xyz_, r1.zxyy, c176.xxxx` — broadcasts `c176.x` to all three color channels) and found a real, likely-significant lead:** it varies between exactly **`0.000`** and **`1.000`** across different draws within the *same frame* (consecutive samples ~60-100ms apart during steady gameplay, i.e. different triangles/body parts of the same character, not different frames). When `c176.x == 0`, the entire cubemap/ambient contribution for that draw is multiplied by zero regardless of what the cubemap texture contains — a complete, silent fill-light dropout for that surface. `c172.x = 0.200` (a related AO/tint scalar used a few instructions later) stayed constant across all samples, so it's specifically `c176.x` that's flipping.

**Caveat, stated plainly since this isn't fully conclusive yet:** a `0`/`1` toggle *could* legitimately be a per-material "has environment reflection" boolean the game sets intentionally (e.g. skin shouldn't pick up mirror-like cubemap reflections the way polished leather/metal straps might) rather than a bug — the shader instance and specific triangle/body-part being drawn weren't captured alongside each sample, so it isn't yet proven that the `0` draws correspond to the visibly-black regions from the 8x boost screenshot rather than to, say, Conan's actual skin (which *should* have low reflectivity) while `1` correctly lights the leather straps. This needs one more correlation step, not a new hypothesis.

**Tested directly and ruled out.** Forced `c176.x` to always read as `1.0` (a one-line write into the register file in the same `UpdateBindings` hook, right before the existing constant-upload loop runs unmodified) and re-ran with the 8x boost still active for a clean visual comparison. **No visible change** — the same shoulder/back highlight, the same pure-black legs and lower torso, pixel-for-pixel indistinguishable from the un-forced boosted screenshot. `c176.x`'s 0/1 toggle is therefore confirmed to be legitimate per-material data (as the caveat above anticipated), not the cause of the missing fill light. Reverted this specific force-override; the rest of the diagnostic instrumentation (the "draw pair" shader-identity logger, and the boost override in `dxbc_translator_om.cpp`) is still in place.

**Status at the end of this investigation session:** root cause still not found, but the search space is now much smaller and well-documented than at the start. Confirmed facts to build on next time:
- Conan's exact three material shaders: `5AC3C8B824ED2F97` (skin), `C66BA6E024478ED7` (leather/straps), `6642CA2D469820DD` (cloth), all paired with skinning vertex shader `B117AD40F2829BDF`.
- The dynamic per-pixel light loop (loop constant 16, relative-addressed `c[64+a0]` etc.) has real, plausible, non-zero data and demonstrably lights *some* surfaces correctly (visible, believable highlight on the upper back/shoulder/forearm under the 8x boost).
- Some other surfaces (legs, lower torso, opposite side of the body) get zero contribution from any source — ruled out `c176.x` (cubemap/IBL scale) as the cause.
- Still unconfirmed either way: the statically-unrolled `c0`-`c23` secondary light array (reads as all-zero; not yet known whether its guard predicates `c182.x`-`c186.x` correctly skip it as unused, or whether it *should* be populated and isn't).
- **Most promising untried angle:** the pattern (some surfaces lit, others completely dark, depending on which way they face) looks exactly like a normal-mapping or per-vertex-normal issue as much as a light-data issue — worth checking whether the surface normal/tangent data reaching this shader is correct for the dark-region triangles specifically, not just the light data. Not investigated this session; flagging as a fresh angle rather than continuing to assume "missing light" is the only possible explanation.

**A follow-on value-level diagnostic attempt failed and is worth recording so it isn't retried the same way:** extended the same hook to dump min/max of the actual float constant *values* uploaded per pixel shader, to check directly for "light color reads as zero." Result was **not usable** — shaders with a declared float_count of 256 showed absurd values (magnitudes around 10^30, with a suspiciously identical `min=-28.4338` recurring across unrelated shader hashes). Root cause: the same "conservative 256-slot" static-analysis effect as above — most of those 256 declared slots are never actually read by the executing shader (guarded by dynamic/bounded indexing), so they hold whatever leftover/uninitialized data happens to sit in the emulated Xenos constant register file at that index. A blind dense scan across the full declared range is meaningless for these shaders; only the specific registers the shader's ALU code actually reads (identifiable from its `.ucode.frag` disassembly, register-by-register) would give a trustworthy answer. Not pursued further this session — flagging as the correct next technique rather than repeating the blind-scan approach.

**Also discovered, unrelated to E041 but worth recording (a real SDK build-system gap, cost a lot of confused iteration before being understood):** `cmake --build out/build/win-amd64 --target install` does **not** reliably refresh `out/win-amd64/<dll>.dll` (the flat path the conan-port project's link step actually copies from) after an SDK-only source change, even when the build itself reports success with no errors. Root cause, confirmed by inspecting `ninja -t query`: this is a Ninja Multi-Config generator, and the real build output lands at `out/win-amd64/RelWithDebInfo/<dll>.dll` — a *different* file from the flat `out/win-amd64/<dll>.dll` the "install"/copy step is supposed to refresh from it. The object files and the `RelWithDebInfo/` copy do get rebuilt correctly; the flat copy just doesn't reliably follow. Two layers of staleness compound this: (1) the SDK's own "install" step not refreshing the flat copy from `RelWithDebInfo/`, and (2) once that's fixed, the *project's* build not re-running its own `copy_if_different` from the SDK's flat path into the project's own runtime directory, because ninja sees no dependency edge from the project's build graph to that external DLL's mtime — the copy is chained as a post-link command on `conan.exe`'s own link step, which won't rerun if none of `conan.exe`'s own inputs (project source) changed. Symptom: SDK rebuild succeeds, project rebuild succeeds, but the *running* game still exhibits the old behavior because a stale DLL is silently still in place two directories deep. **Workaround used:** after any SDK-only rebuild, verify with `ninja -t query "<target>:RelWithDebInfo"` what the real output path is, manually copy `out/win-amd64/RelWithDebInfo/<dll>.dll` → `out/win-amd64/<dll>.dll` (fixes layer 1), then copy that → the project's `out/build/win-amd64-relwithdebinfo/<dll>.dll` (fixes layer 2). Must stop the running `conan.exe` first in both cases — the DLL is locked while the process is up.

Next step: narrow the exact pixel shader (e.g. temporarily forcing each candidate's output to a solid debug color, one at a time, and observing which draw on screen changes), then hand-trace that specific shader's `.ucode.frag` disassembly register-by-register against the actual Xenos register file values for the registers it genuinely reads (not a blind full-range scan) — the same targeted, evidence-based approach that resolved E016-E040, just applied one level deeper now that the shader itself is identified.

**Breakthrough (later session): found the actual root cause mechanism.** The skin shader's statically-unrolled secondary light array (`c0`-`c23`, confirmed all-zero back when E041 was first opened) is gated per-light by a threshold check in the ucode (`setp_gt r0._, c182.x` / `(!p0) jmp L88`, and equivalently `c183.x`/`c184.x`/`c185.x`/`c186.x` for four more light slots): the block only executes - i.e. only actually *uses* that light's data - when its gate constant is `> 0`. Dumped all five gates directly: **`c182.x = 1.0000`, `c183.x = c184.x = c185.x = c186.x = 0.0000`.** The first light slot's gate is **on** (`1.0`, so `setp_gt` is true, the jump-to-skip is *not* taken, the block executes and consumes `c0`-`c9`), while the other four correctly stay off (`0.0`, correctly skipped). This is the exact same bug class as E016-E040: **a "this data is valid/enabled" flag is set correctly, but the data it's supposed to gate was never actually written** - here, static/area light slot 0 is turned on, but its color/position/attenuation constants (`c0`-`c9`) are all zero, so the shader faithfully computes a zero contribution from a light that's flagged as active. This is very likely the fill/ambient light gap identified by the earlier 8x-boost test (E041's "some surfaces stay pure black" finding) - a plausible design is one static "fill" light (slot 0) meant to light the character independent of the dynamic per-pixel loop, exactly matching where the boost test showed nothing.

**Checked the one obvious next hypothesis directly and it's ruled out too: this isn't a "write gets skipped" bug.** Added a counter in the base SDK's `CommandProcessor::WriteRegister` (`src/graphics/command_processor.cpp` - every single GPU register write from the guest's command stream passes through here) filtered to the pixel-constant register range for `c0`-`c9` and for `c182`. Result: writes to the `c0`-`c9` range happen **continuously and repeatedly** throughout gameplay (tens of thousands of hits, steadily incrementing) - so the CPU-side code path is not being bypassed by a guard or an unregistered-function gap the way E016-E040's bugs were. It genuinely executes and genuinely writes **the value zero**, over and over, every frame. `c182` also writes repeatedly, with a mix of zero and non-trivial bit patterns depdepending on which of its four components (x/y/z/w - the diagnostic doesn't distinguish which) a given write targets; the shader-relevant `c182.x` component was separately confirmed (via the direct register *read* above) to hold `1.0` at the moment a draw happens.

**This changes the shape of the remaining problem.** It's not "a data-write got silently skipped" (E016-E040's pattern) - it's "a computation that's supposed to produce a non-zero light color/position for an enabled light instead correctly, repeatedly produces zero." That points toward either (a) the light's *source data* in the game's own scene/level structures genuinely being zero-valued for this slot (a content/data issue, possibly even present on real hardware and not a port bug at all - not yet distinguishable from here), or (b) a computation bug in the specific PPC routine that derives this light's color from whatever it's supposed to be derived from (e.g. reading the wrong field, a scale factor that's zero when it shouldn't be, etc.) - the same general class of subtle arithmetic bug that's much harder to spot than the null-pointer/unregistered-function bugs fixed so far, because it produces a plausible-looking value (zero is a valid float) rather than a crash.

**Not yet done, the clear next step:** identifying *which* PPC function performs this specific write would need call-stack/return-address capture at the point of the `WriteRegister` call - not attempted yet, and only partially useful even if built, since `WriteRegister`'s immediate caller is the SDK's own GPU ring-buffer command processor, not the game's PPC code directly (the actual guest instruction that queued this write lives further back, in the guest command-buffer contents themselves). A more direct path would be a guest-memory write breakpoint via the `windbg-tool`/DbgEng infrastructure already used for E025/E026, targeting whatever guest-side structure this shader's light-setup code reads from - not attempted this session; would need to first identify a plausible candidate address to break on, which isn't available yet without further source-level investigation into the game's own light-management code.

**Attempted (this session) and reverted: a cheaper alternative to a live debugger, using architecture already understood from the E047 investigation.** `CommandProcessor::WriteRegister` (base class) was already confirmed to run on the SDK's own async "GPU Commands" worker thread (`WorkerThreadMain`), not the guest thread - so a breakpoint there genuinely can't see the guest PPC call stack, confirmed by reading the code rather than assumed. The one point that *should* be reached synchronously from the guest thread's own recompiled code is `GraphicsSystem::WriteRegisterThunk` (it receives the real `PPCContext*` as a parameter) - specifically its handling of `CP_RB_WPTR` (the ring-buffer write-pointer "kick" register, `case 0x01C5`), which calls `CommandProcessor::UpdateWritePointer`. The plan: capture the guest `ctx->lr` (return address) and `ctx->r1` (stack pointer) into a pair of atomics on every `CP_RB_WPTR` write, then read them back (throttled) whenever `WriteRegister` sees a pixel c0-c9 write of exactly 0.0f, as a closely-time-correlated (not exact, since one WPTR update can flush a batch of several queued commands) answer to "what guest code submitted this".

**This surfaced a more fundamental, useful finding: `WriteRegisterThunk` is never invoked at all during normal play in this title.** Added an unconditional, throttled log at the top of the thunk (which is guaranteed to fire on its very first call regardless of throttle value, since the counter starts at 0) - it never fired once across a full play session with heavy GPU activity (foliage draws alone triggered thousands of log lines elsewhere in the same session). Yet the game renders correctly and `CommandProcessor::write_ptr_index_` (grepped for every assignment site) is *only* ever written inside `UpdateWritePointer`, which is *only* ever called from this one, apparently-unreached case. This is a genuine contradiction that means **this investigation does not yet understand how the ring buffer's write pointer actually gets updated in this title/SDK configuration** - the standard Xenia-derived MMIO mechanism (`memory_->AddVirtualMappedRange(0x7FC80000, ...)` registered in `GraphicsSystem::SetupGuestGpu`) is registered and should be live, but is empirically not the path being used. Possibilities not yet distinguished: a different/overridden `GraphicsSystem` subclass or code path for this title's configuration, a kernel-export-based ring-buffer kick this investigation hasn't located, or some other mechanism entirely.

**Reverted the LR-capture instrumentation** (both the `WriteRegisterThunk` changes in `graphics_system.cpp` and the readback in `command_processor.cpp`) since it doesn't work as designed and would be dead weight - replaced with a short code comment at both sites recording this finding, so the next attempt starts from "find the real write-pointer-update mechanism first" instead of re-deriving this same dead end.

## E040 (fixed) — a whole vtable-dispatch thunk chain fixed at once, first crash reached during real interactive gameplay

## E034 (fixed) — native SDK crash (not generated guest code) in the audio subsystem, reached after confirming difficulty in a real "New Game" flow

```
[exception_handler] Unhandled exception at host RIP=...: rex::audio::AudioSystem::SubmitFrame+0x1DE
at C:\Users\jrbar\rexglue-sdk\src\audio\audio_system.cpp:276
```
This is **not** recompiled guest PPC code - it's a crash inside the SDK's own native C++ audio subsystem, the first of this kind found this session. **Verification:** rebuilt (SDK + project), reran the same New Game → Medium difficulty sequence - the audio crash is gone, and the game progressed into loading real level terrain data (see E035, immediately below) before hitting a new, different, expected E012-E015-class crash - confirming genuine progress.

## E026 (fixed) — deterministic access violation in the CRT heap-free path, immediately downstream of the E025 fix

**Symptom:** with E025 fixed, the game no longer hangs — it now runs further and then crashes with a genuine, **100% deterministic** access violation (identical guest registers, identical guest fault address, across two independent full process runs). The SDK's own crash handler symbolizes it as:
```
Unhandled guest access violation: write of guest 0x7CC83378 (host 0x000000017CC83378)
[exception_handler] Unhandled exception at host RIP=...: __imp__sub_822DD1C8+0x3FD at conan_recomp.78.cpp:4709
```
with `r29=0x8257AAF0`, `r30=0x40000000`, `r31=0x7024EF50` identical in both runs.

**Investigation:**
- `sub_822DD1C8` (`conan_recomp.78.cpp:4420`) is a low-level memory-free routine — it calls real Xbox kernel primitives (`__imp__KeGetCurrentProcessType`, `__imp__KeBugCheckEx`, `__imp__RtlEnterCriticalSection`, all confirmed genuinely implemented in the SDK, not stubs — checked `src/kernel/xboxkrnl/xboxkrnl_rtl.cpp`) and, on one branch, unlinks a node from a doubly-linked list (classic heap free-list unlink: `Y->prev = X; X->next = Y` at line 4709/4710) using pointers read from a 16-byte block header at `r29-16`. **`r30 = 0x40000000` is not a corrupted pointer** — it's `X_MEM_HEAP`, a real memory-type constant defined in `include/rex/system/xtypes.h:132` (confirmed by grep before assuming corruption, per CLAUDE.md's evidence rule), so this function's first parameter is a type/flags selector, not a "this" pointer. Signature is effectively `(heap_type, flags, ptr_to_free)`.
- The crash is a write through `MEM[r29-48+4]` (`0x7CC83378`), i.e. the block's stored "next" pointer is garbage. Traced backward: `r29`'s source is `r5 = 0x8257AAF0`, passed unmodified from `sub_822DA510` (`conan_recomp.91.cpp:4967`, a small "finalize-then-free" wrapper — the classic C++ scalar deleting destructor shape) which is itself reached from the *exact same call chain that used to hang* in E025 (`sub_82582BF0` → ... → `sub_825870B8`'s region), confirmed via a fresh ProcDump+`windbg-tool.exe` symbolized stack trace on a dump captured with `procdump64.exe -e -ma` (unhandled-exception trigger; a first attempt with `-e 1` over-triggered on the benign `0x406D1388` SetThreadName exception and had to be redone with plain `-e` for unhandled-only).
- **`0x8257AAF0` itself is the real defect, not the free-list unlink code.** `REX_CODE_BASE=0x821D0000`/`REX_CODE_SIZE=0x8106BC` (from `generated/default/conan_pch.h`) puts `0x8257AAF0` squarely inside the executable's own code/rodata range — never a legitimate heap allocation. Reading a fake 16-byte "block header" at `0x8257AAF0-16` picks up whatever static bytes happen to live there; one of them (the flag byte at `+5`, bit `0x8`) happens to be set, sending execution down the "needs free-list unlink" branch, which then reads two more coincidental static-data words as if they were real `prev`/`next` pointers — one of which (`0x7CC83378`) is not a valid address, causing the AV. None of this is a bug in `sub_822DD1C8` itself; it's being handed a fundamentally wrong pointer.
- **Working hypothesis (not yet proven):** this is very likely a *second symptom of the same still-unfound upstream defect* that produced E016-E025's family of null/invalid-`r31` guards in `sub_825870B8` — something before that function runs is building an incomplete or corrupted linked list, and the E025 fix (correctly) lets the traversal finish instead of hanging, but whatever the traversal was supposed to hand back up the call chain (eventually reaching `sub_822DA510`'s destructor call as `0x8257AAF0`) is itself wrong because the underlying list was already bad. This has **not** been confirmed by tracing the actual data flow from `sub_825870B8`'s output to `sub_822DA510`'s input — that is the next step, not a conclusion yet.

**Resolution — traced the exact data flow with temporary logging hooks instead of guessing further, since the live DbgEng continue/wait workflow turned out to be unreliable in this environment** (attaching `windbg-tool.exe` to a live process via `live_launch_session` + `target_set_breakpoint` worked, but `target_continue`/`target_continue_wait` returned `Acceso denegado (0x80070005)` on every attempt after the first, leaving the target permanently stopped — abandoned in favor of native logging hooks, which is a more reliable technique on this toolchain anyway):
1. Added a pure-observer `[[entrypoint.midasm_hook]]` (no `return`/`jump_address` fields at all, so `emit_mid_asm_hook` in the SDK emits a plain call with zero control-flow change) at `sub_822DA510`'s own entry, logging `r3` on every call. Confirmed 613 calls total, the last one exactly `r3=0x8257AB00` (not `0x8257AAF0` — that value is computed *inside* `sub_822DD1C8` itself via `addi r29,r29,-16`, completely normal block-header arithmetic once you have the real object pointer; the actual defect is the object pointer itself, `0x8257AB00`).
2. `sub_822DA510` has exactly one static caller, `sub_822D95C0` (`b 0x822da510`/`b 0x822da4f8` tail-branch dispatcher selecting by bit 31 of an `r4` flags word) — confirmed by grep, not by trusting the debugger's inline-frame stack reconstruction, which turned out to be unreliable to cross-check manually against raw disassembly once the compiler starts folding/inlining these small wrapper functions (a dead end explored and abandoned mid-session — spent real effort trying to match `return_offset`/`instruction_offset` pairs against literal `bl`/`bctrl` text and repeatedly failed to find a matching call instruction near the reported return address, before realizing the debugger's PDB-based inline-frame attribution doesn't require one).
3. `sub_822D95C0`'s own sole caller is `sub_82233220`, a generic tail-call wrapper (`b 0x822d95c0`) — this is a widely-shared `AddRef`/`Release`-style helper called from dozens of unrelated places, so finding *the* call site by grep alone wasn't feasible.
4. Since the manifest's `registers` list has no way to pass `lr` (`emit_mid_asm_hook`'s register switch only handles `r`/`f`/`v`/`c`/`x`-prefixed names), pulled `ctx.lr` directly from `rex::runtime::ThreadState::Get()->context()` inside the hook function instead — the same technique the SDK's own `xmemory.cpp` crash-diagnostic patch already uses. This immediately identified the true caller without needing register-list changes.
5. `sub_825839E0` (the local-object destructor from `sub_82582BF0`'s stack-allocated temporary — same function/object as originally suspected) is the caller, confirmed via its own entry hook: **all 6 invocations** in the run have `lr=0x82582C88`, `sub_82582BF0`'s single shared cleanup call site. That call site is reached by *two* different paths that had looked distinguishable from the static source alone but aren't: the "nothing to do" early-out, **and** the main path after calling `sub_825870B8` (E024/E025's list-walk function) when it returns a negative/error code (`conan_recomp.64.cpp:17169-17174`, `bge`/`goto loc_82582C80` — the exact same label). `lr` alone can't tell the two apart since they converge.
6. Read `sub_825839E0`'s actual body (`conan_recomp.14.cpp:16874-16958`): it has two near-identical guarded blocks, each checking a value field (`+4` or `+8`) and a same-numbered flag byte (`+56` or `+60`) before calling `sub_82233220` (Release) on the value field. The crashing block is the second one (`+8`/`+60`), matching `lr=0x82583A34` seen when logging `sub_822D95C0`'s entry directly.
7. **The actual root cause:** that `+8` field is populated by `sub_825870B8`'s own list-copy loop (`conan_recomp.38.cpp` around line 17512, `stw r11,8(r22)` where `r11 = REX_LOAD_U32(ctx.r31.u32 + 20)` — `r31` being the current list node) with **no validation at the copy site**, copying whatever a list node's `+20` field happens to contain straight into the object that `sub_825839E0` will later unconditionally `Release()`. The value that reaches the crash, `0x8257AB00`, is a code/rodata address (`REX_CODE_BASE=0x821D0000`/`REX_CODE_SIZE=0x8106BC`) — never a legitimate heap allocation, exactly the same class of defect as E018, just surfacing at the *consumption* end of this list walk instead of the *traversal* end where E016-E025's guards all sit. (Why the list node's own `+20` field holds a code-region value in the first place is still not established — could be a real upstream defect in whatever populates this particular list, or could be a deliberate non-pointer use of that field for *some* node types that `sub_825839E0`'s flag-byte check doesn't actually distinguish from "owned object". Not chased further: the fix below is correct regardless of which explanation is true, since a code-region address is never safe to `Release()` either way.)

**Fix applied:** two more `[[entrypoint.midasm_hook]]` entries, reusing E018's existing `conan_valid_code_ptr_guard` **unchanged** but wired with `jump_address_on_true` instead of `_on_false` this time (skip when the value *is* a code pointer, not when it isn't) — one at each of `sub_825839E0`'s two `bl 0x82233220` call sites (`0x82583A10` and `0x82583A30`), each bailing to that same block's own existing "nothing to release" label (`0x82583A14`/`0x82583A34` respectively — the exact labels its own null/flag checks a few lines up already use). A code-region field is now treated exactly like an absent one, instead of being handed to `Release()`.

**Verification:** clean codegen (0 errors), clean rebuild. Reran — the `sub_822DD1C8` heap-free crash is completely gone; the process now runs further and hits a **different, unrelated** crash (see E027) with entirely different registers/fault address/guest function, confirming real forward progress rather than a masked symptom.

All temporary diagnostic-only hooks (`conan_log_destruct_call`, `conan_log_dispatch_call`, `conan_log_finalize_entry` in `src/hooks.cpp`, plus a temporary conditional log in the SDK's `resources/templates/codegen/_indirect_call.inja` that never actually fired — both `sub_822D95C0` and `sub_822DA510` turned out to be reached only via direct `bl`, never through the indirect-call dispatch macro) were removed once the root cause was confirmed, per the same hygiene as the rest of this session's diagnostics.

**Status:** fixed and verified. See E027 for the newly-exposed crash.

## E025 (fixed) — game hangs indefinitely at the "Loading..." screen; not a crash, a genuine stall

**Symptom:** after all of E016-E024, a run reaches a real "Loading..." screen (correct artwork, correct text, an animating loading-icon spinner) and then never progresses. Confirmed by the user watching it directly, and independently confirmed here: the process stays alive for 10+ minutes with **two threads continuously accumulating CPU** (`Get-Process` showed both climbing steadily, e.g. 7m→10m over a few minutes of observation) while the runtime's own debug log **stops producing new lines entirely** partway through the loading-screen's own texture-loading burst. No `[FATAL]`, no access violation, no exception-handler output — the process is just busy-spinning on something that never resolves.

**What the log shows right before it goes silent:** the loading screen is still fetching *its own* UI assets (`UI_SHL_LoadScreen_GE_01`, `UI_HUD_RenderText`, `UI_FNT_Mikadan_28`, `dbgfnt0`, etc.) via the same multi-directory `.dds`-then-`.tga` search chain seen in E012/E016. Notably: **`game/levels/*.nes/.ngo/.nwf`** (the actual level geometry files) are never referenced at all in the log — the hang happens before any real level data is even requested, still within loading-screen UI setup.

**Also noted, not yet chased down:** the search-directory list length appears to vary per asset in ways not yet fully explained — `UI_FNT_Mikadan_28.dds`'s search stops after checking only 7 directories (`Textures` → `HUD`) and never tries `Textures\Fonts`, even though `game/textures/fonts/UI_FNT_Mikadan_28.dds` genuinely exists there. Compare `dbgfnt0`'s search, which always tries all 11 directories including `Ui` and the root. This might be a real clue (different search-list length per asset/category, not a universal fixed list) or might be irrelevant to the actual hang; not established either way.

**Diagnosis attempted, hit a genuine dead end (documented in detail so it isn't retried the same way):** tried building a live-process register sampler — suspend a busy thread, read RIP via `GetThreadContext`, resume, symbolize the RIP with the same `dbghelp` machinery as `patches/sdk/0001-crash-diagnostics.patch` — to find exactly what guest code the busy threads are stuck in, the same way RIP-symbolization nailed down every crash above. `scripts/sample_and_symbolize.ps1` went through three iterations:
1. Plain P/Invoke `ref CONTEXT64 ctx` parameter — `GetThreadContext` returned `ERROR_NOACCESS` (998) every time. Most likely cause: the real x64 `CONTEXT` structure is declared `DECLSPEC_ALIGN(16)`, and a normal marshaled `ref struct` parameter doesn't guarantee that alignment.
2. Manually 16/32-byte-aligned raw buffer via `Marshal.AllocHGlobal` + pointer arithmetic, passed as a plain `IntPtr`. **Confirmed the thread-suspend/resume calls themselves never damaged the target process** across every attempt (checked `TotalProcessorTime` kept climbing normally on the sampled thread both before and after each attempt — the risk of leaving a thread suspended was considered and actively checked, not ignored). But calling the script against the *real* `conan.exe` process reproducibly failed with no output at all and an unusual exit code (116/127) — reproduced identically via two different invocation styles (`powershell -File`, `& script.ps1` from both the Bash tool and the PowerShell tool). The **same script with a placeholder invalid PID/TID (`-ThreadIds 1 -ProcessId 1`) ran cleanly** and printed the expected "access denied" message, meaning the script itself parses and starts fine — something about calling `GetThreadContext`/`OpenProcess`/`SymInitialize` against the real, many-module conan.exe process causes an unmanaged-level failure severe enough that a C# `try`/`catch` around the whole script never even gets to run its `catch` block. That pattern (no catchable exception, process-level exit code) is consistent with an actual access violation inside the unmanaged Win32 call itself — i.e. attempt 2's alignment/size still wasn't right, and calling it for real risks crashing the *diagnostic tool's own host* (`powershell.exe`), not just failing gracefully.
3. **Abandoned the PowerShell approach** rather than iterating further on hand-rolled `CONTEXT` marshaling — the risk profile changed (attempt 1 failed safely, attempt 2 didn't). Pivoted to an **in-process native watchdog instead**, which worked and produced real evidence (below).

**In-process watchdog (`patches/sdk/`, `KernelState::DumpAllThreadContexts()` + a detached `std::thread` in `Runtime::Setup()`, see the source for full comments):** dumps every registered guest thread's full 32-GPR + LR/CTR state, 30s after boot then every 10s for 6 samples. Far safer than the PowerShell approach (native, in-process, no cross-process marshaling) and it worked immediately. Findings, confirmed across three separate runs:

- Of ~43 registered threads, most are an idle worker-thread pool sitting at the same dispatch point (`lr=0x822DDDB8`) with sequential handle values (`r3` incrementing by `0xC` per thread) — that's a normal idle thread pool, not the problem.
- **One thread (guest thread ID varies by run, e.g. `0x00000006`) is genuinely stuck**, and — this is the important part — **all 32 GPRs plus LR/CTR are bit-for-bit identical across samples taken 10 seconds apart.** That rules out an active PPC-level spin loop: any loop, even a trivial counter, would change at least one register between two samples 10 seconds apart. A frozen `PPCContext` this complete means the thread is blocked inside **host** code (a kernel wait primitive, a mutex, or an inline MMIO handler call triggered from `REX_MM_LOAD`/`REX_MM_STORE` — none of which touch `PPCContext` while blocked), not spinning in guest code.
- `lr=0x825873E4` in every run — this is the return address into `sub_825870B8` (the same giant function from E021-E024) right after a call to `sub_825662C0`, which turned out to be a **hand-written PPC `memset`** (byte-align loop, then 16-byte-unrolled `stw` loop, then a small tail loop — classic PPC libc `memset(dest, val, count)` shape, confirmed by reading its full disassembly/generated code). The destination pointer (`r6`) sits at exactly `r3 + 28` — i.e. **the full 28-byte memset had already completed** by the time of the first sample. So execution is not stuck inside the memset itself.
- What happens immediately after that return (per the generated `.cpp`) is a short run of unconditional `lwz`/`stw` pairs reading through `r31`-based struct fields, no branches, before the next `bl`. `r31` at sample time reads as `0x00000000` in its low 32 bits (`Register` is a plain union over `{u32, u64, ...}`; the high 32 bits shown, e.g. `0x7024F010`, are just leftover garbage from a previous 64-bit store into the same register, standard behavior confirmed by reading `include/rex/ppc/context.h`'s `union Register`). A null `r31` dereferenced by the very next `lwz` should crash, not hang — since it doesn't, execution almost certainly has **not** reached that particular straight-line code yet, which means `r31`'s value at the sample point is not the "this" pointer role that field played earlier in the function (E021/E022 already established that `sub_825870B8` reuses `r31` for different purposes across its ~36,000-line body) — i.e. the disassembly-reading shortcut that worked for every earlier guard (find the code right after the `bl`/`ctx.lr=` line) does not reliably identify the *currently executing* line once a function this large reuses registers this heavily; the static line-after-the-call is not necessarily what's running right now.

**Conclusion for this session: root-caused down to "blocked in a host call reached from within `sub_825870B8`, shortly after a completed memset, very likely something GPU/render-command-buffer related given this function's role and the game's boot sequence having just reached D3D12 render-target creation" — but not fully pinned to the exact host function without either a real debugger (to get a host call stack, not just the guest PPCContext) or a much finer-grained guest instruction tracer than a 10-second-interval sampler can provide.** This is genuinely the point where a real debugger (`WinDbg`/`cdb`, neither installed on this machine) would resolve this in minutes via a host stack trace, versus more hours of PPCContext archaeology. Flagging this explicitly rather than continuing to guess.

**Do not, on a future attempt:**
- Re-derive "which guest function is at fault" purely by reading the static disassembly right after a `bl`/`ctx.lr=` assignment once inside `sub_825870B8` specifically — this function is confirmed to reuse GPRs including `r31` for different roles across its body, so that shortcut (which worked for every other guard in this session) is unreliable here.
- Assume a frozen `PPCContext` means a crash is imminent or that the thread is "about to" do something — it's been static for 10+ seconds across every observed run, meaning whatever host call it's blocked in has been blocked at least that long, every time.

**Not yet attempted:**
- Grepping `src/kernel/` for the specific wait primitive (`KeWaitForSingleObject`/`NtWaitForSingleObjectEx`/event/semaphore) this particular stall might be blocked on — the kernel does have real implementations of these (not obvious stubs), so if this is a producer/consumer stall, it's more likely a genuine timing/ordering issue between guest threads than a missing kernel feature, but this has not been confirmed either way.
- Checking whether the search-directory-list-length inconsistency noted above is connected to the hang, or is an unrelated, separate observation.
- Letting a run sit for much longer than 10 minutes, in case it's merely extremely slow rather than truly stuck forever (considered unlikely given zero new log output for that whole window, but not conclusively ruled out).

**Resolution — built a full offline symbolic-debugger pipeline per explicit user authorization ("busca una forma de diagnosticarlo y arreglarlo con herramientas que puedas instalar y usar sin mi intervención, no importa que sea trabajoso"), since the in-process watchdog above hit its ceiling (PPCContext-only, no host call stack):**
- Installed, all no-admin/no-network-account: Sysinternals **ProcDump** (`C:\Users\jrbar\tools\procdump`, portable zip from Microsoft's own download), Python **`minidump`** package (explored, not ultimately needed), and the real Microsoft **DbgEng engine** (`dbgeng.dll`/`dbghelp.dll`/`dbgcore.dll`/`dbgmodel.dll`) via the `devolutions.windbg.tool.win-x64` NuGet package (a plain zip from `api.nuget.org`), which ships a self-contained `windbg-tool.exe` exposing 148+ MCP-style debugging tools over a local daemon (`dump_open_session`, `target_list_threads`, `target_thread_context`, `target_stack_trace`, `target_last_event`, `target_disassemble`, etc.) — no Visual Studio/WinDbg install needed.
- Captured a full dump of the hung process (`procdump64.exe -ma <pid>`) and opened it with `windbg-tool.exe`. This is the first time in this session a **real, PDB-symbolized, multi-frame call stack** (not just a single-point register snapshot) was available for a stuck thread.
- Thread `system_id 7296` (of 82 total OS threads — the other ~78 confirmed as the normal idle worker pool, matching the watchdog's earlier finding) showed a 22-frame stack rooted in the guest thread entry (`xstart` → `rex::system::XThread::Execute` → ... → `sub_825870B8`), with **frame 0 sitting exactly at `conan_recomp.38.cpp:17573`** — the `cmplwi cr6,r31,0` compare inside the **E024 guard's own condition check** at guest address `0x8258748C`.
- Reading the surrounding generated code (`conan_recomp.38.cpp:17542-17614`) revealed the actual bug: **E024's fix itself was wrong.** The guard at `0x8258748C` (`lwz r31,80(r31)`, a linked-list "next" pointer read) bailed to `jump_address_on_false = 0x82587450` when `r31` was null — but `loc_82587450` is **not** an exit; it's the *outer loop's own re-entry point*, which re-tests that same (now-unchanged) `r31`, finds it still null, and branches straight back to `0x8258748C` — directly back into the guard. Since the guard's failure path never modifies `r31`, this is a hard two-instruction infinite loop (`82587450 → 8258748C → guard-false → 82587450 → ...`), not a crash — and it fully explains the watchdog's frozen-PPCContext observation from the original diagnosis: the loop's only state is the already-null `r31`, so nothing in the guest-visible register file ever changes between samples, even though the CPU is genuinely spinning (fast, at the host-x86 level) the whole time. The E024 doc comment's claim that `loc_82587450` was "the same 'done' target this loop's own subsequent null check already uses" was simply incorrect — verified false by reading the real control flow, not assumed.
- **Fix:** changed `jump_address_on_false` for the `0x8258748C` hook (`conan_manifest.toml`) from `0x82587450` to **`0x825870F8`** — the genuine "list exhausted" exit that the surrounding code already falls through to (see the `bne 0x82587450` / `b 0x825870f8` pair right after this same load) when the freshly-loaded `r31` turns out to be null. Making the "null before the read" case jump to the same place as the "null after the read" case makes the two paths semantically identical, which is exactly what should have been done in E024.
- **Verification:** clean codegen (0 errors) + clean rebuild. Relaunched twice (`run37`, `run38`) — the hang is gone; the process now runs past this point and reaches a new, different, fully deterministic point (see E026) instead of stalling. No regression in the milestones already reached (splash video, loading-screen art, "Loading..." text still render correctly per the log).
- **Root-cause note for later:** E024's guard (like E016-E023 before it) treats a *symptom* — `r31` being null/invalid at a specific read — without knowing *why* it's null. It is very likely this whole family of guards (E016-E024) is band-aiding a single, still-unfound upstream defect that produces a genuinely incomplete/corrupted linked list somewhere before `sub_825870B8` ever runs. See E026, which is very likely a second symptom of that same unfound upstream cause.

## E009 — project build: `use of undeclared label 'loc_XXXXXXXX'` in generated code (5 instances)

**Symptom:** after fixing E007/E008, `cmake --build` fails compiling two `generated/default/conan_recomp.*.cpp` files with `error: use of undeclared label 'loc_XXXXXXXX'`. The analyzer sealed both halves as independently-valid, complete functions (each has its own real `mflr`/`stwu` prologue, which is why this wasn't caught by codegen's validation — nothing was actually *unresolved*), and only the writer's file-partitioning step exposed the problem, by putting the two halves in different output files.

**First fix attempt (didn't work):** used the manifest's `parent` field (`[entrypoint.functions.0xCHILD] parent = 0xPARENT`) — the mechanism that *did* work for E005. Root cause of the non-fix: `registerChunk()` (`src/codegen/function_graph.cpp`) only feeds `FunctionGraph::isVacant()`, which blocks *future* gap-fill/discovery candidates from claiming that region — it does not merge the chunk's code into its parent's output file, or otherwise change where the writer phase emits it. **Actual fix:** override the *first* function's own `size`/`end` directly (no `parent` entry on the second address at all) so the entire fall-through range becomes **one** sealed function with the same `FunctionAuthority::CONFIG` priority as any other manifest override. With nothing left to independently claim the second address as its own function, there's no separate file for its label to end up in — the branch is just an ordinary local label inside one function. `end` for each was the second function's own already-correct end (next differently-shaped, unrelated function's start, verified in the disassembly):

| First (overridden) | end | absorbs |
|---|---|---|
| `0x82645498` | `0x826455B0` | `0x82645534` |
| `0x82652AAC` | `0x82652BC4` | `0x82652B48` |
| `0x8265E768` | `0x8265E880` | `0x8265E804`, `0x8265E858` (a third link in the same fall-through chain — the debug log's "contains pdata" notice caught this, see below) |

## E008 — project build: `rex/ui/style.h:18: fatal error: 'imgui.h' file not found` compiling `rex_app.cpp`

**Symptom:** after fixing E007, `src/main.cpp.obj` and (an absolute-path source) `.../rexglue-sdk/src/ui/rex_app.cpp.obj` both fail with `imgui.h` not found.

**Root cause:** genuine inconsistency between the SDK's two supported consumption modes, not a bug in this project's manifest or generated code. `rexglue_configure_target()` (called by `rexglue_setup_target()` in `generated/rexglue.cmake`) compiles the SDK's `rex_app.cpp` directly into the host executable target (`conan`), and that file needs `imgui.h`. In the **installed-package** mode (`find_package(rexglue)`), this works by accident: the SDK's install step flattens every header — its own plus every vendored third-party one (`imgui.h`, `fmt`, `spdlog`, `toml++`, SDL3, …) — into one combined `include/` directory, and the imported `rex::runtime` target's `INTERFACE_INCLUDE_DIRECTORIES` is just that one flat directory (confirmed by reading `rexglueTargets.cmake`). ## E004/E005/E006 — the 3 first-pass `UnresolvedCall` errors (Analyze: found 3 errors)

**Symptom:** first-pass `rexglue codegen conan_manifest.toml` (no `--force`) sealed 51,962/52,018 functions but failed validation with 3 `UnresolvedCall` errors:
```
0x82700B80 from 0x82714FE4: b 0x82700B80 from 0x82714FE4 - target not in any function
0x824577CC from 0x824577DC: b 0x824577CC from 0x824577DC - target not in any function
0x82280078 from 0x82798C28: b 0x82280078 from 0x82798C28 - target not in any function
```

**Investigation method:** wrote [`scripts/xex_decode.py`](../scripts/xex_decode.py), which decrypts (AES-128-CBC, zero IV, the standard published Xbox 360 XEX2 retail key — read directly out of the SDK's own `rexglue-sdk/src/system/xex_module.cpp:xe_xex2_retail_key`, not guessed) and decompresses (`compression_type=1`, "basic": alternating data/zero-fill block runs, decoded from the XEX's own `XEX_HEADER_FILE_FORMAT_INFO` header) `game/default.xex` into a flat memory image. Verified byte-exact: reconstructed size (14,483,456 bytes) matched the header's declared `image_size` (`0xDD0000`) exactly. Disassembled the result with the SDK's bundled `tools/binutils/powerpc-none-elf-objdump.exe -b binary -m powerpc -EB --adjust-vma=0x82000000` and grepped around each address (evidence: `logs/default_full.dis`, `logs/codegen_trace1.txt`).

**Classification (CLAUDE.md Phase 5 decision tree) — all three are Category B/C, real code the analyzer failed to seal, not missing imports/data/jump tables:**

- **E004 (`0x82700B80`):** standalone leaf function — `addi r11,r3,4 / lwz r10,4(r11) / addi r3,r10,1 / stw r3,4(r11) / blr` (5 instructions, 0x14 bytes, bounded by zero-padding before the next unrelated function at `0x82700B98`). Grepped the whole disassembly: its only reference anywhere in the binary is a `b` (tail call, not `bl`) from `0x82714FE4`, ~86 KB away. Never `bl`-called, so it had no evidence to seed a function entry under any of the analyzer's discovery heuristics (import thunk, vtable slot, PDATA, jump table). **Fix:** `[entrypoint.functions.0x82700B80] end = 0x82700B94` in the manifest — declares it as its own function with a verified boundary.

- **E005 (`0x824577CC` / `0x824577D4`):** **not** an independent function at all. The real function starts at `0x82457768` (one of a repeated family of tiny "switch on a type-tag field" accessor functions at `0x82457600/.../0x824576E0/0x82457768/0x824577E8`) and its own internal branches (`beq cr6,0x824577D4` at `0x824577B8`, `bge cr6,0x824577CC` at `0x824577C0`) reach into what the analyzer had wrongly seeded as a second, separate function starting at `0x824577D4`. Grepped every reference to `0x824577CC`/`0x824577D4` in the whole disassembly: all three (`0x824577B8`, `0x824577C0`, `0x824577DC`) originate from inside `0x82457768`'s own body — there is no external caller anywhere. **Fix:** the manifest's chunk mechanism (`parent` field), not a standalone function override — `[entrypoint.functions.0x824577D4] parent = 0x82457768 end = 0x824577E0` folds the mis-seeded block back into its true parent. This alone left one residual error (the shared 2-instruction epilogue `li r3,0 / blr` at `0x824577CC`, reached from three different points including the newly-declared chunk, wasn't itself covered by either the parent's or the chunk's declared range) — needed a **second** chunk entry for that block too: `[entrypoint.functions.0x824577CC] parent = 0x82457768 end = 0x824577D4`. Takeaway for next time: a chunk's `end` only covers its own declared range — a shared block reached by both the parent and a chunk needs its own chunk entry, declaring one function's boundary doesn't retroactively absorb every block that branches into it.

- **E006 (`0x82280078`):** standalone constructor — writes a vtable pointer + zero-initializes several fields, 10 instructions/0x28 bytes, bounded by the next function's start at `0x822800A0` (verified no gap/padding is being swallowed). Part of a dispatch-table family of `{lis/addi/b}` trampolines at `0x82798C10/0x82798C20/0x82798C30/0x82798C40`, each of which sets up an object pointer then tail-calls the matching constructor — the sibling trampolines' targets (`0x8227F1C0`, `0x82280780`, `0x822810D8`) already resolved fine on their own. `0x82280078` is the one target that immediately follows a `bctr` (indirect-branch-terminated) function with **no** zero-padding gap, unlike its siblings' targets — the working hypothesis is that gap-fill's "new function candidate" heuristic doesn't fire right after a computed-jump instruction the way it does after padding, though the *fix* doesn't depend on confirming that root cause, only on the address being real, bounded, self-contained code. **Fix:** `[entrypoint.functions.0x82280078] end = 0x822800A0`.

**Verification:** after all 4 manifest entries, `rexglue codegen conan_manifest.toml` (still no `--force`) reports **0 analysis errors** — `Analyze: found 3 errors` → 1 → 0 across three iterations, each iteration re-run and re-diffed before moving on (never batched all 4 entries blind). Final run: "Codegen summary: 275 written... Done in 25.7s", 52,022 functions partitioned across 134 output files. Full manifest comments recording this evidence live in `conan_manifest.toml` itself, next to each override.

**Status:** fixed and verified. This is milestone **M3 (zero analysis errors)** for this title.

## E041 continuation - found the actual packet mechanism: one huge shared constant upload, confirmed sparse

Kept going past the previous entry's stopping point, since the ranked leads it identified (the second `sub_822F8300` caller, the unexplored `+21648` field) turned out to be dead ends within minutes of checking them: the second caller's own containing function builds a fixed 19-dword generic event/notification buffer unrelated to graphics, and `+21648` turned out to be a ubiquitous field referenced from ~70+ completely unrelated places across the whole binary (a common base-class field, not light-specific) - both ruled out immediately, not worth further tracing.

**Went back to the actual GPU command stream instead of more guest-code tracing, and this time found the real packet.** Added overlap-detection logging (`[E041-scan]`/`[E041-scan2]`/`[E041-scan3]`, `src/graphics/command_processor.cpp`, temporary) to every single PM4 code path that can reach `WriteRegister` for the `c0`-`c9` index range, one at a time, ruling each out empirically instead of assuming:
- A literal ring-buffer byte scan for the exact `SET_CONSTANT` header dword (`0x00000400`) - zero hits.
- `WriteALURangeFromRing` (inline `SET_CONSTANT`, ALU-typed) and `ExecutePacketType3_LOAD_ALU_CONSTANT` (memory-sourced ALU load) - both instrumented to log any range overlapping `0x400`-`0x427` - zero hits from either.
- **`ExecutePacketType0` (the simplest, most direct PM4 mechanism - packet header directly encodes an absolute register base index and count) - hit immediately and constantly**: `base_index=0x4400 count=1008` (up to `count=1024`, varies slightly), firing continuously throughout gameplay. This is one **enormous bulk register upload** - 1008-1024 consecutive registers (252-256 float4 vectors) in a single packet, covering the *entire* pixel float-constant bank in one shot, not a small per-light write.

**Peeked directly into this packet's own payload from inside the ring buffer** (before it's consumed) rather than continuing to infer from `WriteRegister`'s per-word view:
- The 32 registers immediately after `c0`-`c9` (`0x4428` onward) are **also all zero**.
- Sparse-sampling the *entire* 1008-1024-word packet (every 7th register) found it **overwhelmingly zero, but not entirely**: 2 out of 144 samples non-zero, first hit at relative register offset `644` (well outside the `c0`-`c9`/`0x400`-`0x427` range), value `0x3F950200` - a **plausible real float** (~1.16) if reinterpreted as IEEE-754.

**This is a real, independent (not PPC-tracing-derived) confirmation of the "shared, mostly-empty constant buffer" model already suspected from the shader-side investigation** (the five `c182`-`c186` light-slot gates): the game builds *one* large combined float-constant buffer covering many potential material/light/etc. slots, uploads the *whole thing* every relevant kick via a single Type-0 packet, and only a **small, sparse subset** of it actually holds real per-frame data - the rest, including our target `c0`-`c9` slice, stays at its default zero. This matches exactly: light slot 0's gate (`c182.x=1.0`) says "populated", but its 10-vec4 data slice in this shared buffer is empty, same as every other unused slot in the buffer - the shader has no way to tell "legitimately zero" apart from "gate says enabled but slice was never written", so it renders a zero-contribution light that's flagged as active.

**What this does and doesn't tell us:** it confirms, independently, that the previously-identified shader-side symptom (gate open, data empty) is real at the GPU-command level too, not an artifact of the shader-constant readback diagnostic. It does **not** yet identify which PPC code is supposed to write into this buffer's `c0`-`c9` slice specifically - the buffer's payload is written directly into ring-buffer memory by ordinary guest stores (not a separate memory-sourced `LOAD_ALU_CONSTANT`), so there's no single "loader" function to inspect; whoever assembles this buffer writes it inline, likely as part of a much larger command-list-building pass this investigation hasn't located yet. A live guest-memory write-watch on the buffer's own slice (the same technique already proven for the `0x82B6D128` state-cursor fix) is the concrete next step for finding that writer directly, rather than continuing to guess from static disassembly - not yet attempted, given the ring buffer's address changes with every kick (unlike the state cursor's fixed address), so the watch would need to be re-armed per-kick against the *current* kick's own range, a moderate but bounded amount of new plumbing.

**Diagnostics added this session, all temporary** (`src/graphics/command_processor.cpp`): `[E041-scan]` (per-kick ring-buffer literal scan in `UpdateWritePointer`), `[E041-scan2]` (`WriteALURangeFromRing`/`ExecutePacketType3_LOAD_ALU_CONSTANT` overlap checks), `[E041-scan3]` (`ExecutePacketType0` overlap check + sparse whole-packet sampling, the one that found the real mechanism). ## E041 continuation - found a second, parallel broken initialization chain; real but risky, reverted after a crash

Traced backward from the descriptor array itself (per the previous entry's next step) to its submission function, `sub_822DF100`, and found something significant: **this function has two entirely separate, mutually-exclusive paths**, gated by a per-object counter at `object+11000`:
- **"Simple" path** (always taken while the counter is `0`, which is where it starts and where 3 of its 4 call sites permanently leave it - they pass a hardcoded increment of `0`): calls `sub_822DEC70`, the entire chain this investigation has spent most of its time on, now conclusively shown to never carry color data.
- **"Rich" path** (only reachable once the counter is nonzero): calls a completely different, never-before-examined function, `sub_822DE8B8`.

**Found the one and only call site that ever makes the counter nonzero** (`0x822F3B98`, passes `r7=1` where the other three pass `0`), and traced backward from there through a real, concrete gate: `sub_824F1CC0` checks `MEM[sub_8254DF10()] > 1` (a global that `sub_8254DF10` trivially always resolves to a fixed address, `0x82CBE654` - not a computed value) before allowing the whole enabling chain to proceed. Live-read that global directly (`[E041-probe21]`): it's `2`, comfortably passing the gate - **the global itself isn't the problem**. But a probe placed directly on the gate check inside `sub_824F1CC0` (`[E041-probe20]`) got **zero hits across a sustained ~4-minute session including active movement** - the function containing the check is never called at all. Searched for static callers (none - it's reached only indirectly, e.g. a stored function pointer) and scanned the image's data regions directly for literal references to its address: found two, one inside the code range (almost certainly a disassembly-of-data artifact, not a real reference) and one in genuine data (`0x82A25B88`, a `{func_ptr, 0, 1, another_ptr}`-shaped repeating table) - could not find what code actually reads that table (likely array-indexed at runtime rather than through a literal fixed-immediate address, which a static text search can't find). Did not pursue further given time already spent; a live debugger with a data breakpoint on that table would resolve this quickly where static analysis can't.

**Tested the seed-the-counter approach directly anyway** (same safe, data-only pattern as the original state-cursor fix - write `object+11000 = 1` once, let the game's own already-compiled code do the rest): it worked in the sense that the game's own code genuinely called `sub_822DE8B8` for the first time ever in this port. **It immediately crashed** - a null-pointer write (`stw r30,0(r31)` with `r31=0`), traced to `MEM[object+13360]` being null. That field turns out to be a **second, separate prerequisite** this "rich" subsystem needs (a write-cursor into a growable buffer whose allocation logic - found via the same field's other reference sites - is *itself* gated behind yet another unmet precondition earlier in the same broken chain). Seeding one field in isolation isn't enough; the real fix needs whatever's supposed to initialize this whole subsystem together, not a field-by-field patch-up. **Reverted the seed immediately** (see the `E041-fix-attempt-4` comment left in place in `src/hooks.cpp` for the full writeup) and rebuilt/verified back to the known-safe baseline - no regression, state-cursor fix (gap 1) still active and verified.

**Assessment:** this is real, hard evidence of a *second*, structurally similar broken-initialization bug (the same "state that should have been set up together during a proper init sequence never runs" pattern as the original `0x82B6D128` cursor), but on a different, deeper subsystem this session did not fully map out, and unlike the original fix, seeding a single field here is not sufficient or safe - it trades one crash for another. Whether this "rich" path is even the correct mechanism for the specific `c0`-`c9` static-fill-light data this bug is chasing is *also* not yet certain - it was reached by tracing the descriptor-submission function's *other* branch, not by any direct evidence tying it to the shader's fill-light slot specifically. Given the risk profile, do not re-attempt seeding `object+11000`/`object+13360` without either (a) finding the real upstream trigger via a live debugger's data breakpoints (the concrete blocker this session hit), or (b) fully mapping every field this "rich" path touches before its first genuine c0-c9-affecting write, so a complete, consistent seed can be applied in one step instead of one crash-and-patch at a time.

**Diagnostics added this session:** `[E041-probe19]` (descriptor compact-reference resolution, confirmed correct), `[E041-probe20]` (the never-firing quality gate check), `[E041-probe21]` (the quality global's live value, confirmed fine), `[E041-scan5]` (one-shot image-data scan for references to the gate function's address, in `OnPostLoadXexImage` via `conan_e041_scan_for_caller_reference` in `src/hooks.cpp`/`src/conan_app.h`). **Follow-up in the same session: independently confirmed the dormant "rich" subsystem is completely unreachable (not just its outer gate), and traced its purpose deep enough to conclude it's very likely unrelated to color data anyway.** Added a direct entry probe (`[E041-probe23]`) on `sub_822F3A10` - the function containing the one call site that ever passes a nonzero increment to `sub_822DF100` - independent of the `sub_824F1CC0` gate probe, in case there was a second path in. Also went back and properly read `interface+4` (the field the "commit" dispatch calls through, previously only resolved via a single live pointer read) instead of continuing to treat it as an opaque "commit" black box. It resolves to a **trivial bounds-check utility** (`cmplwi`/`bgtlr` against a fixed constant `6212` - "is `[offset, offset+size)` within capacity", returning a boolean) - not a shader-constant writer of any kind. **Also discovered, while re-reading `sub_822F8740` in full for the first time (previously only its `field+816` write had been examined):** it zeroes a specific, complete set of interface fields on every allocation - `784, 792, 796, 800, 804, 808, 812, 820, 828, 832, 836, 840, 844, 848, 852` - i.e. it explicitly establishes the "known-zero" starting state for exactly the fields opcodes `96-99`/`84` write into later. **Tried one more angle: watch the gate constant (`c182.x`) itself instead of `c0`-`c9`, on the theory that whoever writes the gate might be simpler to find and its sibling code might be the real color writer.** Added `[E041-lr2]` in `command_processor.cpp` targeting absolute register `0x46D8`. **This address is now independently verified correct** (not just assumed): `include/rex/graphics/register_table.inc` defines `XE_GPU_REG_SHADER_CONSTANT_000_X = 0x4000` (each float4 constant is 4 dwords), and the D3D12 layer's own pixel-constant upload code (`d3d12/command_processor.cpp`, `UpdateBindings`) uses `XE_GPU_REG_SHADER_CONSTANT_256_X` as the pixel-constants base - i.e. flat constant 256 = `0x4000 + 256*4 = 0x4400` (matching `c0`), and constant `256+182=438` (`c182`) = `0x4000 + 438*4 = 0x46D8`, exactly what was watched. Also separately confirmed `SQ_PS_CONST` (register `0x2308`, a state register, not part of the constant data) is asserted elsewhere in the same file to normally hold `0x000FF100`, which decodes (per its documented bitfield) to `base=256, size=256` - independently corroborating the same `256` base assumption from a completely different angle.

Result: 231 hits, **all `value=0x00000000`** - never once non-zero, genuinely contradicting the earlier, already-documented finding that a direct D3D12-side constant-buffer readback showed `c182.x = 1.0`.

**Chased and ruled out the obvious explanation (a register-usage-map bug in the shader translator causing the D3D12 layer to skip copying `c0`-`c9`/`c182`-`c186` even if the base register file held real data) within the same session, cheaply, by reading the translator's own logic** (`src/graphics/pipeline/shader/translator.cpp`): `constant_register_map_.float_dynamic_addressing` gets set whenever the shader uses register-relative addressing for float constants (exactly what the skin shader's *dynamic* per-pixel light loop does, `c[64+a0]`) - and when set, the translator forces `float_count = 256` and marks *every* bit in `float_bitmap` as used (`memset(..., UINT8_MAX, ...)`), specifically because dynamic addressing means the compiler can't know in advance which indices will actually be touched at runtime, so it conservatively includes everything. This exactly matches what `[E041-diag]` has shown for this shader all along ("256 float4 constants"), confirming this path is taken. **This rules out the translator/usage-map hypothesis for this specific shader**: `UpdateBindings` does copy the full `c0`-`c255` range from the base register file into the bound constant buffer, unfiltered, precisely because of the dynamic-addressing forcing rule - there's no bitmap-based skipping happening for `c0`-`c9`/`c182`-`c186` to be a suspect.

**Net effect: the D3D12 copy-out layer is confirmed innocent (copies the full range faithfully), which pushes the unresolved discrepancy back onto either (a) this session's write-watch missing a rare/transient non-zero write among unwatched or infrequently-throttled samples (`[E041-lr2]` only logs 1-in-5 hits, and this session's live capture spanned a few dozen seconds, not the full range of scenarios a full playthrough might hit), or (b) the earlier "1.0" reading having come from stale/reused constant-buffer-pool memory left over from a *different* shader's draw, if `UpdateBindings`'s allocation (`constant_buffer_pool_->Request`) doesn't guarantee zeroed/fresh memory for every request** - a real, testable, but not-yet-tested possibility given this session's time constraints. Either way, this session's own `c0`-`c9` writes are conclusively, independently confirmed dead (zero for the entire base register file's relevant range, verified three separate ways: `[E041-lr]`'s per-word watch, `[E041-scan3]`'s in-packet payload sampling, and `[E041-scan4]`'s cross-kick byte-identical diffing) - the discrepancy is specifically about `c182.x`'s gate value, not about the color data itself, and does not change this session's central, multiply-confirmed finding that the color data never arrives.

**Resolved the discrepancy, and found the cleanest, most comprehensive confirmation of E041's whole mechanism to date.** Extended `[E041-lr3]` to dump all 24 static-array floats (`c0`-`c23`) alongside all 5 gates (`c182.x`-`c186.x`) together, at actual constant-buffer bind time for the skin shader specifically, sampled continuously (not just once) while Conan was on screen and moving. Result, across many samples: **the gates genuinely toggle dynamically** - different combinations of `c182`-`c186` are active on different draws (e.g. `c183=1,c184=1` on one draw, `c183=1` alone on the next, all-zero on another) - this is not a static/frozen state, it's a real, working per-draw light-slot selection system. But **`c0` through `c23` read exactly `0.000` on every single sample, regardless of which gate(s) were active**. This is not the narrower "slot 0 only" bug the previous session characterized - it's confirmation that **the entire statically-unrolled 5-slot light array is data-dead across all slots**, while the gate/selection logic that decides *which* slot should matter on a given draw works perfectly. The earlier session's single-sample "`c182.x=1.0`" reading wasn't wrong or stale - it just happened to catch a moment when slot 0 specifically was the active gate; this session's broader, continuous sampling shows the same zero-data symptom holds for every slot, not just that one.

This meaningfully sharpens the problem statement for whoever continues E041 next: the bug is in whatever CPU-side mechanism is supposed to feed **all five** static light slots' data (a single shared writer/buffer most likely, given the uniform failure across slots), not a slot-0-specific code path - which also means the `sub_822DEC70`/interface/byte-code-interpreter chain this session spent most of its time on, even if it turns out to be involved, would need to explain data for *all five* slots to be the right mechanism, not just one light's worth of descriptor entries. Whether that's consistent with what's already been traced (one interface, one light, one 11-entry descriptor) or points toward a *different*, not-yet-examined per-frame system that aggregates multiple lights into this shared 5-slot array is the open question for the next session.

**Closed the loop with one final, properly-filtered check**: extended `[E041-lr3]` to also log the kick-correlated guest LR (`current_kick_`, directly accessible from `D3D12CommandProcessor` since it's a protected member of the base `CommandProcessor` class it inherits from - no new plumbing needed) alongside the bind-time gate/data dump, so the LR is now filtered to *specifically* Conan's skin-shader draws rather than being an unfiltered, potentially-cross-contaminated sample the way `[E041-lr]`/`[E041-lr2]` are (raw `WriteRegister`-level watches can't distinguish which shader's `SQ_PS_CONST.base` a given absolute register write belongs to, so they mix in unrelated shaders reusing the same absolute register slots - this is *also* the resolved explanation for this session's earlier "`c182.x` always 0" raw-watch finding: that watch was catching mostly other shaders' data at the same absolute address, not Conan's). Result: **every single sample's kick LR is `0x822DED28`** - the exact same address this entire investigation, across every session, has consistently traced back to (`sub_822DEC70`, right after its own vtable dispatch call). This is a clean, trustworthy confirmation that the investigation has been looking in the right neighborhood all along, even though the exact missing write within that neighborhood remains unfound - it rules out the possibility that Conan's actual color-bearing draw is kicked from some entirely different, unexamined code path.

**One more structural discovery worth recording for continuation: found the shared parent that calls both `sub_822DEC70` (this whole session's main thread) and a second, previously-only-partially-traced sibling system, as alternate branches of the same per-object update.** Tracing `sub_822DE600`'s own callers (found earlier this session, at `0x822DFEF8` and `0x822F2ADC`) led to `sub_822F2A90`: a **global state-change detector** - it compares a tracked global value (`MEM[MEM[0x82000000+1412]]`, an indirected global pointer) against a per-object cached copy (`object+348`), and only when they differ, updates the cache and calls `sub_822DE600` with a type tag (`r5=2`, matching one of the `0xC000600N`-style type-tag constants already seen in this session's raw memory dumps around the *other*, `sub_822DF100`-reached resolved descriptor pointers - a genuine cross-reference between these two previously-separate investigative threads). `sub_822F2A90` is itself called from `sub_822F2F60`, which - in a **different branch of the same function**, gated by unrelated-looking flag bits (`object+40`, `object+100` bit 30) - calls `sub_822DEC70` directly (with a different calling convention than the one this whole session has traced: `r5=1` fixed, not walking a light array). This confirms `sub_822DEC70` and the state-change/notification chain are siblings under one shared per-object dispatcher, `sub_822F2F60` - useful map of the surrounding code for whoever continues, but tracing `sub_822F2A90`/`sub_822DE600`'s ultimate consumer (through `object+21648`'s raw function-pointer call, `type=2`) did not, in the time available this session, reach anything that looks like a direct float-constant writer either - it remains, like everything else found today, notification/event-dispatch shaped rather than data-writing shaped.

**Final lead of this session: traced backward past the point of *consumption* for the first time, into where the light-array entry itself gets built** - everything up to now only ever examined code that reads an already-existing descriptor. `sub_822DF100`'s first call site builds its "light array" argument by calling `sub_822DF018` first (`0x822DF7C8`) - a function not examined until now. It writes a mix of fixed sentinel/type-tag constants (`0xC0003B00`, `0x7FFF`, `0xC0025800` - the same "extension marker" constant already identified elsewhere this session) interleaved with real, object-derived values, into a local stack buffer. Critically, it then **conditionally writes two of those real, non-sentinel values (`r5`, `r6`) into a third, previously-unexamined structure** (`MEM[object+10896][0]`/`[4]`) - gated on **both** `object+21508` (the light interface) being non-null **and** bit 30 of a flag byte at `object+10941` being set.

Live-probed this gate directly (`[E041-probe24]`/`[E041-probe25]`, 28 samples across roughly 90 seconds of real gameplay): `object+21508` (interface) reads **exactly `0` on every single sample**, and bit 30 of `object+10941` is **also always clear** - neither condition is ever satisfied, so this write never happens, for the whole session. This is a real, additional, previously-unfound instance of the same "flag never gets set" bug class as the original `0x82B6D128` root cause - but pursuing it raised a genuine puzzle rather than resolving cleanly: `object+21508` is independently, robustly confirmed (via `[E041-fix]`'s "POPULATED" log, still firing correctly every session) to become non-null shortly after the game starts - yet `sub_822DF018` consistently reads it as `0`, including in samples taken many tens of seconds into a session where the interface is known to already be populated. This session did not have time to resolve why - either `sub_822DF018` runs at a point in the frame *before* the per-tick interface-population code executes (an ordering question, not examined), or there is a second, distinct object/field being read here despite the matching `object=0x404FA500` (also not yet ruled out). Also worth noting: `r6`, one of the two gated values, is not the array's entry count as first suspected (an early coincidental resemblance to the known `count=11` from unrelated small sample values) - a longer capture shows it's a **large, steadily-growing counter** (~1000 higher every ~5.5 real seconds, consistent with a high-frequency per-tick counter, not an entry index) - most likely a timestamp/sequence value for cache invalidation purposes, not light data itself.

**This is the concrete, best-defined next step for continuation**: resolve why `sub_822DF018` sees a null interface when `object+21508` is independently confirmed populated elsewhere in the same object's lifetime (frame-ordering vs. object-identity), and separately, determine what `object+10941` bit 30 is supposed to represent and why it's never set - either one, if fixed with the same safe, data-only seeding pattern as the original state-cursor fix (once properly understood, unlike this session's two field-seeding attempts that turned out to need more prerequisites than expected), could be the missing trigger for real color data to finally reach `object+10896` and, from there, potentially the shader's `c0`-`c23` static light array.

**Follow-up in the same session, with much tighter (untruncated, 400-sample) probes on both gate conditions simultaneously**: precisely correlated `object+21508` and `object+10941` bit 30 against each other, tick by tick. Searched every `stb` write site for `object+10941` (7 found) for one that actually sets bit value `2` (the bit this gate checks). Found exactly one unconditional match, `ori r11,r11,2` at `0x822DF91C`, inside a function (`sub_822DF848`) that turns out to be an **extremely widely-shared generic utility - over 70 call sites spanning nearly the entire image** (`0x822DE200` through `0x82580F74`), almost certainly a generic list/array "remove entries" helper reused across many unrelated subsystems, not something specific to light or color setup. Continuing to chase why the interface doesn't stay populated (the deepest, most-invested thread in this whole file) would never have led to a fix - it's a real, secondary subsystem (still not understood), but not the one gating `c0`-`c9`.

**Correction to an earlier session's dismissal of `object+10896` as "uninitialized garbage"**: that conclusion (`object+10896 = 0xFFC9B000`, "nowhere close to any guest pointer range this whole investigation has ever seen ... almost certainly uninitialized garbage") is **wrong**, confirmed two ways this session: (1) Xenia shows the *same* value pattern (`0xFFCA3000`/`0xFFCA2000`-range) at the same offset, in a title that renders correctly - a real reference implementation would not have garbage here; (2) the Xbox 360's PowerPC address space reserves its top range (`0xE0000000`+) for physical/uncached memory aliases, which `0xFFCxxxxx` falls squarely inside - entirely consistent with a legitimate, intentional pointer for a GPU-adjacent structure (which "light data" plausibly is), not corruption. **This means the earlier decision not to seed `object+10941` bit 30** (reasoned as unsafe specifically *because* `object+10896` looked like garbage it would crash on) **was based on a false premise** and may be worth revisiting with this corrected understanding, once the physical-address-aliasing question below is resolved.

**Traced one concrete consumer of `object+10896` statically to strengthen this**: `sub_822DE550` (`generated/default/conan_recomp.3.cpp:4426`) reads `MEM[object+10896]` and dereferences `+60` from it as part of a wraparound/clamp range calculation (masked against `object+14876`), then on success calls `sub_822DDE90` (`conan_recomp.108.cpp:4744`) which builds a small record: `[0]=object, [4]=index, [8]=MEM[MEM[object+10896]+0], [12]/[16]=MEM[MEM[r13+256]+88]` (a global/TLS-rooted context pointer), `[20]=REX_QUERY_TIMEBASE()` (a hardware cycle-counter timestamp) - the shape of a **timestamped record being appended to a queue**, structurally consistent with everything else this investigation has found (ring buffers, command queues) but reached via a completely different entry point (`sub_822DE550`, called with `object+10952`/`object+10956`-derived arguments) than anything previously traced. `object+10952` was read live from Xenia during a real write-hit on this exact call and shows a real, non-zero, plausible value (`0x00001325`) - not yet compared against our own build's value at the same live moment (blocked by a `target memory` read failure - see below).

**Physical-memory-aliasing theory: checked and ruled out.** Dispatched a research agent to read `src/system/xmemory.cpp` (this SDK's memory subsystem, a near-verbatim port of Xenia's own `memory.cc`) end to end. Confirmed: the Xbox 360's `0xE0000000`-`0xFFFFFFFF` physical/uncached alias range (which `0xFFCA0000`-range values fall inside) is correctly implemented - a single OS-backed memory-mapped file provides overlapping views for `0x00000000`/`0x40000000`/`0x80000000`/`0xA0000000`/`0xC0000000`/`0xE0000000`, so a normal pointer dereference through any of these ranges automatically aliases to the same physical page, exactly like Xenia's own (and real hardware's) behavior; `REX_PHYS_HOST_OFFSET`'s `+0x1000` correction for the `0xE0000000`+ range is a deliberate, correct compensation for `MapViewOfFileEx`'s 64KB-granularity rounding, not a bug. No TODO or known-limitation comment exists for this. **This SDK subsystem is not the cause of E041** - ruled out with high confidence, don't re-investigate this specific angle.

**The `object+10896`/`+10952` live-read failure against our own build (separate from the Xenia reads, which worked fine) remains unexplained** - `"El sistema no puede leer desde el dispositivo especificado" (0x8007001E)`, even for the XEX image base and the object base itself, addresses that were readable via the identical technique earlier in the very same session. Tried a full windbg-tool daemon restart; didn't resolve it. Most likely explanation given the memory-subsystem finding above: this specific relaunch's heap allocation simply didn't place `object` at `0x404FA500` this time (the "stable across sessions" pattern noted earlier this investigation may be observation bias from always testing a similar navigation path, not a true invariant) - not a sign of any deeper bug. Not resolved before time ran out this session; re-locating the object fresh each session (rather than assuming the fixed address) is the straightforward fix for a future attempt.

**Net assessment of this detour**: the two most-invested leads from the entire multi-session E041 investigation (the `object+21508` interface/rich-path chain, and the `object+10896` physical-pointer-looks-like-garbage theory) are now both conclusively closed - the first because Xenia proves it's irrelevant to a working render, the second because the SDK's memory subsystem is confirmed correct. Neither produced the fix, but both stop being productive avenues for any future session, which is real progress even though the actual root cause remains open. The most concrete unexplored lead from this session is `sub_822DE550`/`sub_822DDE90`'s "timestamped record" pattern (reached from `object+10952`, confirmed live in Xenia to hold real non-zero data `0x00001325`) - but its actual purpose (event/timing log vs. genuine light-color submission) was not confirmed before time ran out, and the LR-correlation technique that flagged it only proves *temporal* proximity to the real `c0`-`c9` write, not that this function *causes* it - treat as an unconfirmed hypothesis, not a established lead, for whoever continues this next.

**Session status**: E041's visible symptom is partially, inconsistently improved (some poses/draws show real skin tone, others - including the specific idle pose directly compared against Xenia - still look wrong) via the constant-buffer patch; the DXBC-injection attempt is reverted after a regression. Honest assessment for the next session: guessing at either the constant-buffer values or a flat output tint has not converged on a fix that matches Xenia's reference rendering. The two most promising real next steps, neither attempted yet: (1) fully decode the `c0`-`c23` light-record format (position/radius/color packing, per-slot) by reading the *entire* gated block for one shader instruction-by-instruction rather than skimming the first/last few lines, so a *correctly shaped* synthetic light record can be constructed instead of a naive flat fill; or (2) return to the CPU-side root-cause hunt (the `sub_822ED860` one-shot-dispatch reframing and the still-untraced `sub_822F2F60` command-buffer source, both documented above) to recover the *real* data instead of faking it.

**This is now the third independently-confirmed-dormant "extended/rich lighting data available" gate found across this object's state** (`object+10941` bit 30, `object+10942` bit 30, `object+11000` word's bit 30/mask `0x2`) - three different consumers, reached via three different call paths (one via `object+21508`'s interface, one via a global-singleton-dereferenced critical section, one via a per-node embedded command queue), all checking what is functionally the same kind of "is rich data populated" flag, and **all three are always clear** during live, reproduced gameplay. This is a strong convergent signal, not three unrelated dead ends: it points at a single missing initialization/construction-time step - most likely a bulk template/prototype copy that should populate this whole `~10900`-`11003` region of the object's state in one shot (consistent with why no *explicit* per-bit setter exists for any of the three - a `memcpy`-style bulk init wouldn't show up as an `ori`/`stb` bit-set at all) - that never runs anywhere in this port. **Best next step for a future session**: instead of continuing to check individual consumer-side gates (three checked, all dormant, diminishing returns), search for the object's *construction/allocation* site and any "copy default light template" style call near it - the previously-reverted `object+13360` null-pointer crash (see the `[E041-fix-attempt-4]` entry above) is itself likely a symptom of this same missing bulk-init step, since a proper template copy would have populated that field too.

## E048 — Low in-game framerate after the E041 work: accumulated debug instrumentation in hot paths

Symptom: the game ran visibly below 60 FPS where it had previously run well above it,
and far below what xenia-edge manages on the same machine, while an external RTSS
overlay reported ~280 FPS. The two numbers disagree because RTSS counts host Present
calls, which keep ticking at display rate regardless of how fast the *guest* is
producing frames - so it was measuring the wrong thing entirely.

Root cause was not one bug but a pile of investigation-era instrumentation, all of it
in per-frame/per-draw/per-instruction paths, left behind by E016-E047:

1. **Guest-memory write-watches (worst offender).** `conan_e041_pump_state_watch()`
   armed `EnablePhysicalMemoryAccessCallbacks` on two guest physical pages - one of
   them the character object's own page, which the game writes constantly. That works
   by write-protecting the page, so *every* guest store into it took an access
   violation into the exception handler and back.
2. **23 mid-ASM probe hooks** still registered in the manifest, running inside
   recompiled guest code (per light, per object, per frame), each doing atomic
   counter work - and each forcing the recompiler to spill registers around a call.
3. **Ring-buffer scanning per kick** in `UpdateWritePointer`: a dword-by-dword,
   byte-swapping scan of the kick's whole ring range, plus a mutex and a deque push.
4. **Per-packet snapshot + memcmp** of 40 constant registers in `ExecutePacketType0`,
   on the bulk constant upload that happens every frame.
5. **Per-draw work in `IssueDraw`**: an E047 detection scan over every non-indexed
   draw, plus unconditional logging on every clamped draw.
6. **A watchdog thread** that, 30s after boot, took the *global kernel critical
   region* six times at 10s intervals to dump every thread's registers.
7. **Guard hooks** (the real E016-E026 crash fixes, which stay) each doing two atomic
   RMWs per call, on paths measured at over a million calls per session.
8. **Input polling** logging every frame while any button was held.
9. **The E041 NaN scan itself**, which had been generalized from an 11-shader
   allowlist to *every* pixel shader, scanning the full uploaded constant range on
   every draw.

Fixes applied: all instrumentation removed; the NaN scan gated to shaders whose
declared constant count indicates dynamic addressing (the only ones that can hit the
bug) and vectorized four floats at a time; the per-draw constant upload changed to
coalesce runs of used constants into bulk copies (256 tiny memcpys -> 4 for a
dynamic-addressing shader); guest spinlocks and the GPU worker's idle loop now
PAUSE-spin briefly before falling back to a `SwitchToThread()` syscall; Windows builds
moved off `-mcmodel=large` (every global/function reference was a 64-bit absolute for
no reason on a ~50MB image); Release relaxed from `-ffp-model=strict` to `precise`
(same IEEE values, no fast-math) and given `-fno-math-errno`; texture cache budgets
raised from 384/768 MB, which at 3x3 resolution scale left the cache evicting textures
still in use every frame.

Verification: the debug overlay (F3) now has a real stats source - `IGraphicsSystem::
guest_frame_counter()`, derived from the guest's own swap count - so "Guest: N FPS" in
the overlay is the honest number, unlike any external overlay. Measured 88-92 FPS in
the cathedral level after the changes.

Open avenue, deliberately not taken: guest memory accesses in generated code are
`volatile` (see `REX_LOAD_*`/`REX_STORE_*` in the codegen template), which blocks
redundant-load elimination across the whole recompiled image. Removing it is likely the
single largest remaining win, but a guest spin-wait loop with no intervening call could
then be hoisted into an infinite loop - a hang is a worse outcome than the frame time,
so this needs a way to test it properly first.

### E048 continuation — second pass, GPU-side

The first pass was all CPU (removing instrumentation). Reported result: "mejorado
considerablemente" but still with drops in specific areas. Second pass targets the GPU
backend's defaults, two of which were costing real work every frame:

1. **`readback_memexport` defaulted to true** while the per-backend flags it supersedes
   (`d3d12_readback_memexport`, `vulkan_readback_memexport`) both default to false - so
   it was silently overriding them and enabling GPU->CPU readback of every memexporting
   draw. The "fast" path is double-buffered and usually avoids a stall, but any change
   in exported size recreates the readback slot, and that path calls
   `AwaitAllQueueOperationsCompletion()` - a full pipeline flush mid-frame. A scene
   whose exported workload varies (particles, skinning) therefore stalls intermittently,
   which matches the "drops in some parts" symptom exactly. Now defaults to false,
   matching the per-backend flags; `--readback_memexport` turns it back on for a title
   that genuinely reads exported data on the CPU.

2. **`primitive_processor_cache_min_indices` defaulted to 0**, meaning every converted
   index buffer got a cache entry no matter how small. The comment directly above the
   cvar documents the upstream default as 4096 and records that even 1024 measured
   *worse* than not caching on one title, because each insertion takes the global
   critical region and protects guest pages. Raised to 4096, so small conversions skip
   the locking and just get redone.

Also checked and deliberately left alone: the EDRAM path already selects the fast
`kHostRenderTargets` (RTV) route on NVIDIA rather than the much slower ROV one; async
shader compilation is already on with a 12-thread creation pool; occlusion queries do
not block the CPU (they check the fence and give up rather than waiting); the texture
cache eviction walk is an LRU list that breaks immediately when under budget, so the
raised budgets from the first pass don't add per-frame scanning.

Next avenue, not taken: kQuadList primitives (the jungle foliage system) are emulated
with a geometry shader, which is a slow path on modern NVIDIA hardware.
`force_convert_quad_lists_to_triangle_lists` would replace it with a cached CPU index
conversion and an ordinary triangle-list draw. It was left off because the E047 clamp
only applies to *non-indexed* kQuadList draws - converting them produces an index
buffer, the clamp would stop matching, and the stretched-foliage bug would come back.
Doing this safely means moving the vertex-count clamp to before
`primitive_processor_->Process()` first.

### E048 continuation — quad lists off the geometry shader path

Taken after all, once the E047 interaction was made safe rather than avoided.

Quad lists were drawn as line lists with adjacency and expanded by a geometry shader.
GS is a slow, partly serializing stage on current hardware, and this title uses quad
lists heavily - the jungle foliage and its shadow-caster pass are built from them, which
is the same content as the reported drops. `force_convert_quad_lists_to_triangle_lists`
now defaults to true: the primitive processor turns them into an ordinary triangle list
drawn through a *built-in, pre-generated* index buffer, so the conversion costs nothing
per draw and the pipeline drops the GS entirely (the backend picks its topology and
geometry shader from `host_primitive_type`, which becomes kTriangleList). The two
repeated indices per quad are absorbed by the post-transform vertex cache, so this
doesn't add vertex shader work.

The blocker for doing this earlier was that the E047 clamp tested
`index_buffer_type == kNone`, which only matches the unconverted path - enabling
conversion would have moved these draws to `kHostBuiltinForAuto` and silently dropped
the protection, bringing the stretched foliage back. The clamp is now expressed against
`guest_draw_vertex_count` (what the guest's vertex buffer capacity actually constrains)
and covers both auto-indexed forms, converting the result to host indices via
`PrimitiveProcessor::GetQuadListTriangleListIndexCount` - the same helper the conversion
itself uses, made public so the two can't drift apart. Genuinely guest-indexed draws
(kGuestDMA, kHostConverted) are still excluded, since there the index buffer, not the
vertex count, decides what gets read.

Verified in the jungle level: foliage, dappled canopy shadows and the cast character
shadow all render as before the change.

### E049 — host timer granularity was setting the frame cadence

Symptom: with vsync on the game sat at ~30 FPS, with vsync off it ran fast but
hitched, and the reported present rate (108) was roughly twice the rate the game
actually animated at.

Root cause: nothing in the process ever raised the Windows timer resolution, so
the scheduler tick stayed at its ~15.6ms default. Every millisecond-granular
wait in the emulator is quantized to that tick - `::Sleep`, `WaitForSingleObject`
timeouts, and therefore every guest `KeDelayExecutionThread` and object wait the
kernel layer maps onto them.

The guest vblank worker asks for a 16.67ms interval. A 16.67ms deadline misses
the 15.6ms tick every single time and lands on the next one at 31.2ms - exactly
the observed 30 FPS. It was never a 30 FPS cap, it was a beat frequency.

With vsync off the same worker ran on a 1ms interval and polled with a 1ms sleep
that really slept 15.6ms, so each wake-up fired ~15 vblanks back to back. Each
one runs the guest's vblank ISR inline, so the guest got interrupt bursts every
15ms instead of a steady signal.

Fixes:
- `thread::EnableHighResolutionTiming()` (timeBeginPeriod(1)) at runtime startup.
- `thread::Sleep` on Windows now uses a per-thread high-resolution waitable timer
  instead of `::Sleep`, so sub-millisecond sleeps are representable at all.
- The vblank worker waits out the remaining interval instead of polling, and
  delivers at most one vblank per wake-up, dropping the backlog rather than
  running the ISR back to back after a hitch.
- `unlocked_vblank_rate` (default 240 Hz) replaces the hardcoded 1000 Hz
  no-vsync interval. 1000 vblank ISR dispatches per second is pure CPU cost
  above any framerate the GPU can deliver.
- `WAIT_REG_MEM`'s back-off is capped at 500us. The guest's wait hint is in
  milliseconds because on real hardware the condition resolves in microseconds;
  sleeping the full hint just added latency to every CP/CPU handshake.

### E050 — occlusion queries serialized the CPU against the GPU

`EndGuestOcclusionQuery` closed the open submission, then blocked on
`CheckSubmissionFence` until the GPU had finished everything submitted so far,
then read the sample count. That is a full pipeline flush at every query site.
Titles use occlusion queries for sun visibility and lens-flare occluders, which
is why the drops tracked the god-ray shafts.

Now the EndQuery/ResolveQueryData ride along in the submission that is already
open, and the result is picked up on a later frame: each guest sample-count
address keeps its own one-frame-deep history (`occlusion_query_slots_`), the
previous result is reported to the guest, and the fence is only *read*, never
waited on. The first query for a site reports the configured fallback count so
a visibility-gated effect doesn't blink out on its first frame.

Reading the fence directly rather than through `CheckSubmissionFence` is
deliberate - that function uses `submission_completed_` to decide whether to
reclaim command allocators and descriptors, so advancing it from here would make
it skip the reclaim.

### E051 — whole-frame re-upload of guest memory

`clear_memory_page_state` defaulted to true, which drops the valid bit from
every CPU-uploaded shared-memory page at frame end. Everything the next frame
touches - geometry, index data, constants - is then re-read out of guest memory
and re-uploaded, every frame, changed or not. The physical write watches already
invalidate pages the guest writes to, so this is a fallback for writes that
bypass them, and it costs memcpy and upload bandwidth continuously.

Now defaults to false. Re-enable with `clear_memory_page_state = true` in
conan.toml if geometry or texture data is ever observed going stale.
